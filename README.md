# О!дин шаг · прибрежный Адлер (трек «О!дин шаг до идеального отеля»)

Подбор отелей Адлера по пожеланиям, которых нет в обычных фильтрах: гость пишет своими словами
(«тихий номер с видом на море, до пляжа без подъёмов»), а сервис проверяет каждое условие по открытым
картам и расчётам — вид из окон по этажам, путь до пляжа, шум дорог, баров и самолётов — и показывает
источник, дату и уверенность у каждого факта. Чего нельзя узнать из данных, сервис спрашивает у отеля
в кабинете отельера, и ответ сразу учитывается в следующих подборах.

## Быстрый старт

```bash
git clone https://github.com/ostrovok-hackathon-2026/cu5people.git
cd cu5people
cp .env.example .env   # необязательно: без .env работают значения по умолчанию
docker compose up --build
# открыть http://localhost:8080
```

Первая сборка занимает несколько минут (образы Python и Node, зависимости). Демо-данные лежат в репозитории,
база наполняется автоматически при старте — ничего дополнительно запускать не нужно.
Остановка — `Ctrl+C` или `docker compose down`; `docker compose down -v` дополнительно удалит базу с ответами отелей.

Нужны только Docker и Docker Compose v2.24+ (Docker Desktop 4.27+). То же через Makefile: `make up`, `make down`, `make seed`.

## Зависимости и переменные окружения

Рекомендованные ресурсы:
- 2 CPU cores
- 2 GB RAM (в работе приложение использует около 150 MB)
- ~1 GB диска под образы

Сервисы в [`docker-compose.yml`](docker-compose.yml):

| Сервис | Порт | Что это |
|---|---|---|
| `web` | **8080** → 8080 | Интерфейс (React, nginx). `/api/*`, `/docs`, `/health` проксируются в `backend` |
| `backend` | 8000, только внутри сети compose | API (FastAPI) и база SQLite в томе `adler-data`; миграции и наполнение данными — при старте |

Внешняя база данных, кэш и ключи не нужны. Образы собираются в несколько этапов и работают от непривилегированного пользователя.

Переменные окружения (все необязательны, полный список с комментариями — в [`.env.example`](.env.example)):

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `WEB_PORT` | `8080` | Порт интерфейса на хосте |
| `DEMO_MODE` | `true` | Учитывать тестовые ответы отелей из демо-набора (в интерфейсе они помечены) |
| `PARSER_MODE` | пусто → `hybrid` из [`config/models.yaml`](config/models.yaml) | Разбор запроса: `hybrid` (правила + LLM), `offline` (только правила), `groq` (облачная LLM) |
| `GROQ_API_KEY` | пусто | Ключ OpenAI-совместимого API для облачной LLM |
| `CLOUD_LLM_BASE_URL` | пусто → Groq | Адрес OpenAI-совместимого API |
| `CLOUD_LLM_MODEL` | пусто → из `config/models.yaml` | Модель облачной LLM |
| `HYBRID_LLM` | пусто → `ollama` | Какая LLM дополняет правила в `hybrid`: `ollama` или `groq` |
| `DOCKER_OLLAMA_URL` | `http://host.docker.internal:11434` | Локальная Ollama на хосте, если есть |
| `REPLY_PARSER_MODE` | пусто → `rules` | Разбор ответов отельера |

Без LLM всё работает: запрос разбирается правилами. LLM (облачная через OpenAI-совместимое API или
локальная Ollama) лучше понимает свободные формулировки. Например, для облачной модели в `.env`:

```bash
PARSER_MODE=groq
CLOUD_LLM_BASE_URL=https://<провайдер>/v1
CLOUD_LLM_MODEL=<модель>
GROQ_API_KEY=<ключ>
```

## Сидирование

Автоматически при каждом старте `backend`: миграции базы, затем загрузка демо-данных (повторный запуск
не создаёт дубликатов и не стирает ответы отелей). Вручную:

```bash
docker compose exec backend python -m scripts.seed_demo
```

Демо-данные — 25 реальных отелей Адлера и 400 рассчитанных характеристик из открытых данных
(OpenStreetMap, рельеф Copernicus): [`data/demo/`](data/demo), [`data/environment/`](data/environment).

## Маршруты/доступ

- `/` — интерфейс: поиск, выдача с картой, страница отеля
- `/hotelier` — кабинет отельера: вопросы от гостей, ответы, характеристики отеля
- `/health` — `200 OK`, JSON `{"status": "ok", "hotels": 25}` (`503`, если база не наполнена)
- `/docs` — Swagger UI; REST API — `/api/*` ([описание](docs/API.md))
- Тестовые учётные данные не нужны: вход для отелей не реализован в текущей версии,
  кабинет любого отеля открывается без пароля.

## Что попробовать

1. На главной выберите пример запроса или напишите свой, например
   «Тихий номер с видом на море, до пляжа не дальше 500 м» → «Найти отели».
   Над выдачей видно, как понят запрос; отели разделены на «Условия подтверждены» и «Не все условия подтверждены».
   В карточке — ответ на каждую часть запроса словами гостя: «Тихий номер — высокий», «До пляжа — ≈ 320 м».
2. «Источники» у карточки: откуда каждый факт, дата и уверенность.
3. Расплывчатый запрос «Вид из окна без деревьев» не останавливает поиск: подходят отели с видом на море, горы
   или закат, а над выдачей можно уточнить «Какой вид важнее? [Любой] [На море] [На горы] [Закат]».
   «Без деревьев» проверяется расчётом: закрывают ли вид деревья и соседние дома.
   То, чего нет в текущей версии («недорого», «с бассейном»), показано как «не реализовано», поиск идёт по остальному.
4. «Посмотреть номер» — страница отеля: соответствие пожеланиям и на чём основан подбор.
5. Запрос «Нужен номер со шторами blackout и магазин ночью» — у части отелей «нет данных» по шторам →
   «Запросить у отельера» → «Ответить от имени отеля».
6. В кабинете: «Ответить» → «В номерах 301–305 есть шторы blackout. В номере 101 нет штор blackout.» →
   «Проверить данные» → «Подтвердить и опубликовать». Повторите поиск — у отеля появится «Шторы blackout — есть в номере 301».

## Ограничения текущей версии

Цены, бронирование, учёт дат и числа гостей, вход для отелей не реализованы — в интерфейсе это подписано.
Фото отелей иллюстративные и помечены «Фото для примера». Ответы отелей в демо-наборе тестовые и помечены.
Карта использует подложку OpenFreeMap (нужен интернет в браузере); без него показывается схема по координатам.
