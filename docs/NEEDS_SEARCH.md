# Поиск по потребностям гостя

Задача: учитывать **весь** запрос гостя и строить ответ по его словам, а не останавливать
поиск вопросом и не терять то, что не легло в признаки реестра.

Было: текст → условия реестра → если что-то неясно, **стоп** («Уточните запрос», 0 отелей);
то, что не легло в признак, — либо стоп, либо молча «не учтено». Ответ — по признакам
(`quietness_proxy: high`), а не по словам гостя.

Стало:

1. **Разметка на потребности.** Парсер (правила или LLM) режет запрос на части с цитатами —
   `ParsedHotelQuery.needs`. У каждой части тип:
   - `feature` — проверяется признаками реестра («без деревьев» → `view_obstruction_risk`);
   - `any_of` — расплывчатое пожелание из `app/features/concepts.yaml` («вид из окна» → любой
     из видов на море, горы, закат);
   - `unsupported` — проверить нечем («дёшево» → тема «цена»).
2. **Ничего не теряется.** `app/ml/needs.py: complete_needs` добавляет потребность для каждого
   условия и каждой непроверяемой темы, которые парсер не разметил. Признак, названный LLM без
   условия, получает мягкое условие по реестру (`query_desired`).
3. **Поиск запускается.** Расплывчатое — не повод для вопроса: `resolve_concepts` добавляет мягкие
   пожелания по всем вариантам. `needs_clarification` остаётся только для другого города,
   противоречия («рядом с клубами и тихо») и запроса без понятных пожеланий.
4. **Оценка по потребностям.** Группа `any_of` — одна, её польза — лучший известный вариант
   (не среднее): `app/ml/multicriteria.py: aggregate(any_of=…)` и такой же учёт в `weighted_v1`.
5. **Ответ словами гостя.** `HotelSearchResult.needs` — строка на каждую часть запроса:
   `{quote, outcome: matched|partial|unknown|violated|unchecked, text, detail, best_option}`.
   Например: «Вид из окна — на море: широкий вид», «Без деревьев — деревья и дома вид не закрывают»,
   «Дёшево — не реализовано в текущей версии (цена)».
6. **Уточнение по желанию.** Над выдачей — «Какой вид важнее? [Любой] [На море] [На горы] [Закат]».
   Кнопка отправляет уже разобранный запрос с `choices: {"window_view": "sea"}` — без повторного
   вызова LLM; выбор хранится в адресе (`?pick=window_view:sea`).

## Признак «деревья и дома перед окнами» (`view_obstruction_risk`)

Выводится из уже посчитанных сценариев viewshed (`low/base/high`: высота деревьев 0 / 0,6 / 1,0
от измеренной и неизвестных соседних домов), без новых геоданных — `app/features/view_robustness.py`,
провайдер `view_robustness` в агенте. `low` — вид одинаков во всех сценариях; `medium` — сужается
или нужен этаж выше; `high` — при высоких деревьях пропадает. Значение — лучший из видов здания.
Ограничения те же, что у расчёта вида: кроны по DSM 30 м грубые, деревья вплотную к фасаду и
листва по сезонам не моделируются. На демо-срезе: low — 16 отелей, medium — 9.

## Новое понятие без кода

Добавьте запись в `app/features/concepts.yaml`: `label`, `question`, `hint` (для LLM),
`patterns` (для правил) и `options` с признаками реестра уровня отеля. LLM видит понятия в промпте,
правила — по `patterns`; варианты проверяются при загрузке.

## Совместимость и оценка

- Поля `needs`, `options/chosen/question`, `choices`, `HotelSearchResult.needs` — новые и с
  пустыми значениями по умолчанию; старые клиенты не ломаются. Без разметки от парсера
  потребности строит backend.
- Оценка парсера (`scripts/compare_parser.py`) `needs` в сравнение условий не включает; понятие
  `any_of` считается распознанной неоднозначностью. Метрики правил на v2/v3 не изменились
  (requirement F1 0,847 / 0,865); ambiguity accuracy v2 0,881 → 0,881, v3 0,95 → 0,967.
  Разметки эталонов по потребностям пока нет — это следующий шаг ML.
- Замороженные наборы v2/v3 перегенерированы билдером: добавилось только пустое `"needs": []`.

## Не сделано

- Обязательное расплывчатое («вид из окна обязателен») ищется как мягкое; строгое «любой из» — отдельно.
- Ответ LLM поверх досье отеля со ссылками на факты (вариант C) — после стабилизации этой схемы.
- В mock-режиме фронта потребностей нет — там прежние строки критериев.
