# Как автоматически оценить понимание запроса

Отдельный файл: `scripts/compare_parser.py`. Сайт не нужен. Это проверка извлечения
требований из текста, а не качества ранжирования отелей.

## Откуда берётся правильный ответ

В `data/evaluation/queries_gold.jsonl` у каждого запроса есть `text`, `split`,
`expected`. Человек проверяет/исправляет `expected`. Скрипт передаёт модели только
`text`, сравнивает ответ с `expected` и сохраняет ошибки. По умолчанию используются
32 held-out запроса; их ответы не входят в few-shot промпт.

Исходная разметка синтетическая, создана coding assistant. Автоматический подсчёт
не делает её достоверной: перед выводами о качестве нужен независимый человеческий
пересмотр. Для сравнения моделей используйте один зафиксированный набор и промпт.

## Быстрый запуск

Из корня проекта, в активированной `.venv`:

```bash
# Проверить сам механизм без LLM и сети (оценивается парсер правил):
python -m scripts.compare_parser --mode offline --output runtime/metrics_offline.json

# Три реальных запроса к установленной Gemma:
python -m scripts.compare_parser --mode ollama --limit 3 --output runtime/metrics_gemma_smoke.json

# Полный held-out набор. По умолчанию 32 запроса; может занять несколько минут:
python -m scripts.compare_parser --mode ollama --output runtime/metrics_gemma.json
```

В отчёте JSON: `summary` — итог, `cases` — эталон, ответ модели, метрики и ошибка
каждого запроса. Результат сохраняется после каждого ответа. `status: running`
означает незавершённый прогон; `complete` — весь выбранный набор обработан.
Для облака соблюдайте свою квоту; для сравнения облачных моделей с паузами удобнее
существующий `benchmark_models.py`, затем повторная оценка сохранённых ответов:

```bash
python -m scripts.compare_parser --predictions runtime/model_comparison.json --profile local-gemma12b
```

Также принимается JSONL: одна строка `{ "text": "...", "actual": { ... } }`.
Необязательные поля — `error`, `latency_seconds`. Тексты сопоставляются точно,
пропущенные ответы считаются ошибками, дубли отклоняются. Если исходный отчёт был
на трёх запросах, задайте тот же `--limit 3` и split: иначе оставшиеся 29 ответов
справедливо будут отмечены как отсутствующие. Время replay не выдаётся за время LLM.

## Три разных косинусных сравнения

Косинус = скалярное произведение двух векторов / произведение их длин.
Это сходство направления, а не вероятность правильности ответа.

1. `field_cosine`: координата — отдельное поле требования, значение — количество.
   Не требует embedding-модели. Показывает частичное совпадение, но может завышать
   результат. Например, у `<=500` и `>=500` совпадают почти все поля, кроме оператора.
2. `requirement_cosine`: координата — целое условие, включая значение, оператор,
   единицу, scope, обязательность; для soft также вес и utility. Сохраняет связи
   между полями. Перестановка границ интервала не пройдёт как правильный ответ.
3. `semantic_cosine`: необязательные нейросетевые embeddings структурированных
   описаний требований. Полезно для исследования смыслового сходства. Требует
   отдельной embedding-модели; Gemma 12B продолжает разбирать запросы.

Исходный текст запроса исключён из всех трёх сравнений: он одинаков в expected и
actual и мог бы искусственно завысить результат. Пустой вектор даёт `null`, а не 1;
рядом со средним всегда есть число реально оценённых пар. Ошибки генерации не
скрываются: они остаются в error_rate и дают пропуски требований в recall/F1.
Для эмбеддингов пустые наборы требований пропускаются, ошибки записываются отдельно.

Опциональное семантическое сравнение через официальный Ollama `/api/embed`:

```bash
ollama pull embeddinggemma  # отдельная модель embeddings, около 622 MB
python -m scripts.compare_parser --mode ollama --limit 3 --embedding-model embeddinggemma
# Или без повторного вызова Gemma:
python -m scripts.compare_parser --predictions runtime/metrics_gemma_smoke.json --limit 3 --embedding-model embeddinggemma
```

Скрипт сам ничего не скачивает. `truncate=False` запрещает незаметно обрезать
описания требований при превышении контекста embedding-модели.
Источники: https://docs.ollama.com/api/embed и https://ollama.com/library/embeddinggemma.

## Что считать основными метриками

- `requirements.precision/recall/f1`: совпадение целых требований. Ошибочное условие
  даёт FP и FN. Сначала суммируем TP/FP/FN всех запросов (micro), затем делим.
- `fields.precision/recall/f1`: более мягкий диагностический срез отдельных полей.
- `exact_match`: совпадение нормализованного контракта, включая регион, непонятные
  требования и формулировку уточняющего вопроса. Порядок списков, original_text и
  ignored_terms не учитываются; метрика отличается от старого evaluate_parser.
- `hard_exact_match`: все обязательные условия совпали целиком, включая границы.
- `operators`, `numbers`, `negations`: precision/recall/F1 специальных срезов.
  Срезы чисел/операторов отдельно не сохраняют их взаимосвязь — поэтому нужны
  целые требования. Negations охватывает False и удалённость от баров; это не
  универсальная оценка всех русских отрицаний.
- `error_rate`: неудачи парсера, некорректный контракт и отсутствующие predictions.
- `latency`: медиана и p95 времени парсера вместе с повторами; embeddings и поиск
  отелей в это время не входят. В replay время берётся только из сохранённого отчёта.

Если знаменатель метрики равен нулю, записывается `null`. У маленькой выборки p95
нестабилен. `needs_clarification` — допустимый ответ, а не техническая ошибка;
его правильность проверяется относительно разметки.

Не назначайте правило «cosine > 0.8 значит правильно»: фразы «есть вид» и «нет вида»
могут быть семантически близкими. Ещё пример: дублирование всех условий сохраняет
cosine=1, но ухудшает precision. Для решения, стала ли модель лучше, используйте
F1 целых требований, hard_exact_match, ошибки и время. Cosine — вспомогательная
диагностика, отдельный порог требует калибровки на человеческой разметке.

Следующие полезные проверки: пары с отрицаниями (`не ближе`/`не дальше`),
эквивалентные единицы (`0.5 км`/`500 м`), перефразировки одного запроса. Для выбора
между двумя моделями можно считать bootstrap-интервалы разницы F1 на тех же запросах.
Эти расширения и оценка ранжирования nDCG@5 не реализованы данным скриптом.

## Выполненные проверки

- 21 тест скрипта и связанных адаптеров прошёл; 7 из них — новые регрессионные
  проверки метрик (отрицания, связь числа с оператором, дубликаты, ошибки, replay).
- На 32 held-out запросах парсер **правил** offline получил F1 целых требований
  0.9315, exact match 0.71875. Это не результат нейросети.
- Gemma 12B проверена на первых 3 held-out запросах: 3 корректных ответа,
  медиана времени 4.12 с, p95 18.76 с. Выборка слишком мала для оценки качества.
- Установлена EmbeddingGemma и проверен `/api/embed` на реальных векторах.
  Для намеренно неправильной замены `<=500` на `>=500` semantic cosine = 0.99396,
  field cosine = 0.75, requirement cosine = 0, exact match = false.
  [Сохранённый пример](examples/cosine_counterexample.json) показывает,
  почему высокий semantic cosine не доказывает правильности извлечения.
