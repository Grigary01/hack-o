## Пять обязательных требований задания

### 1. Агент выбирает источники и вычисляет хотя бы одну Geo-характеристику

Реализовано для MVP: FeatureAgent выбирает кэш, Geo-инструмент или вопрос по реестру.
Есть реальный пешеходный граф и вычисляемые виды/окружение. Rule-based агент допустим:
задание не требует LLM-планировщика. В выборке 25 отелей и 375 геонаблюдений.
Ограничение: при существующем неизвестном/устаревшем hotel-факте агент выдаёт trace
`request_snapshot_refresh`, а не выполняет обновление или универсальный fallback к отельеру.
Код: app/agent/feature_agent.py:45, app/geo/service.py.

### 2. Вопрос отельеру, свободный ответ и извлечение

Реализовано в ограниченном демонстрационном сценарии. Вопросы создаются при нехватке
сведений о номере; простые предложения с номерами, этажом и отрицаниями разбираются
правилами. Перед записью требуется подтверждение. Симуляция разрешена заданием.
Сложные условия, исключения и сезонность требуют уточнения; это не универсальное NLU.
Ответ сохраняется, но выдачу гостя нужно пересчитать — автоматического push/polling нет.
Код: app/hotelier/dialogue.py, app/api/hotelier.py, frontend/app.py.

### 3. Хранение, источник, уверенность, дата, противоречия

Реализовано: Observation/Evidence, TTL, история, конфликтующие значения, явное решение
оператора в кабинете (app/hotelier/review.py). TASKS.md с TODO про resolver устарел.
Конфликт значений одного факта блокирует использование; конфликт «отельер о номере
против модели здания» показывается предупреждением и сам по себе не исключает номер.
Уверенность не калибрована: low/medium нельзя выдавать за вероятность правильности.

### 4. Расширяемость

Реализовано через YAML и провайдеры: новое boolean-свойство номера с существующим
hotelier-провайдером добавляется без переделки архитектуры. Новый физический расчёт
всё равно требует нового вычислителя/источника. Нельзя обещать произвольную новую
геохарактеристику только по текстовому описанию.

### 5. Поиск своими словами

Реальный путь работает: Gemma → JSON → инструменты → факты → ранжирование → UI.
Но качество пока недостаточно для заявления «всё выполнено»: есть потери обязательных
условий и добавление отсутствующих в запросе условий. Pydantic проверяет структуру,
но не защищает от смысловых ошибок. Также нарушен повторный запрос после изменения весов.

## Найденные проблемы по приоритету

### P0 · ML + Backend: потеря обязательных требований пропускает все отели

Gemma на «Нужен обязательно шумоизолированный номер» вернула пустые hard/soft,
без вопроса и без списка непонятного. API принимает это как поиск без ограничений:
25 matched. На «Обязательно вид на море и шумоизоляция в одном номере» обязательность
заменена двумя мягкими пожеланиями. На «Вид на море не нужен» добавлены пляж <=500 м
и тишина, которых пользователь не просил.

Нужно: разобрать ошибки промпта, проверить явные обязательные/отрицательные/численные
условия, не продолжать поиск с молча потерянным содержанием. Пустой разбор содержательного
запроса должен запросить уточнение. Добавить сквозные регрессионные тесты, а не только
проверку валидного JSON. Код: app/ml/prompts.py, app/ml/query_parser.py, app/api/search.py:20.

### P0 · ML + Backend: после смены весов следующий пересчёт даёт 422

app/api/search.py:32 меняет `weight_source` на explicit, но оставляет `derived_from`.
Валидатор app/schemas/query.py:111 разрешает derived_from только с companion.
Ответ API после обновления весов оказывается непригоден для следующего входного запроса.
Frontend сохраняет такой parsed и отправляет повторно (frontend/app.py:128).

Нужно согласовать происхождение признака и происхождение веса как разные понятия;
проверить цепочку search → изменение веса → повторное изменение → ответ отельера → поиск.
Существующий UI-тест проверяет отсутствие исключения, но не гарантирует отсутствие st.error.

### P1 · ML: малая важность может сильно изменить выдачу

В app/ml/multicriteria.py:63 вклад худшей группы равен 25% независимо от её веса.
Воспроизведение: важность тишины 1, пляжа 0.001. Соответствия A=(1,0), B=(0.9,1).
Итоги: A=0.74925, B=0.90007. Почти неважный пляж перевешивает лучшую тишину.
Это свойство выбранной формулы, а не ошибка арифметики; его нельзя выдавать за
проверенную модель предпочтений пользователя.

Нужно: определить желаемую семантику веса, проверить близкий к нулю вес, нулевой вес,
монотонность и сравнить v1/v2 по человеческой оценке. Варианты исправления — взвешенный
штраф за дефицит или отключение balance до обоснования; победителя без разметки нет.

### P1 · ML: автоматически выведенные желания не всегда следуют из запроса

- У «номер без вида на море» добавляется пожелание `sea_view_potential=none` для всего
  здания (registry.yaml:64). Номер во двор в здании с морским фасадом тоже подходит,
  но такая связь необоснованно снижает рейтинг отеля.
- При весе тишины 0 автоматически добавленная удалённость от самолётов остаётся с
  весом 0.72, если отдельно не поменять её вес. Нужно явно решить, наследуются ли веса.
- Hard `до пляжа <=500 м` не добавляет подъёмы/переходы; soft «рядом с пляжем» добавляет.
  Само по себе это не нарушение запроса, но нельзя говорить, что рельеф и переходы
  всегда учтены во всех поисках близко к пляжу. Код: app/ml/companions.py:31.

### P1 · ML + Geo: достоверность и совместимость признаков не полностью входят в оценку

Свежесть/конфликт/unknown учитываются, но low и medium при одинаковом значении дают
одинаковый match. Hard может пройти по оценке с низкой уверенностью; есть предупреждение.
Интервал рейтинга отражает только отсутствие данных, а не погрешность измерения.
Потенциалы моря/гор/заката берутся по лучшим фасадам/этажам независимо: их совместное
наличие у одного окна не доказано. Проверка same-room работает для фактов конкретных
номеров, но расчётные потенциалы здания её не заменяют.

Нужны политика использования оценочных фактов в hard и явное различие между
«может быть где-то в здании» и «есть в предлагаемом номере». Не назначать произвольные
вероятности low=0.3/medium=0.7 без калибровки.

### P1 · ML: нет эталона и метрик качества ранжирования

Есть тесты математики, но нет независимых оценок пар запрос–отель и замера nDCG@5,
Precision@5 или доли реальных нарушений обязательных условий в выдаче.
Для первого эксперимента: 20 запросов × 25 отелей = 500 оценок по фиксированному
срезу фактов; unknown отмечать отдельно. Часть оценок дать второму человеку.
Это предложенный объём для MVP, не обязательный стандарт. Обязательно сравнить v1/v2
на одинаковых кандидатах и одинаковом parsed, чтобы отделить ranker от ошибок LLM.

### P2 · Backend/Geo: актуализация требует ручного полного цикла

Trace агента рекомендует `scripts.refresh_geo --refresh`, но эта команда без --apply
лишь создаёт отчёт. --apply меняет JSON-данные, не рабочую SQLite; затем нужен seed.
Обновляются виды, а не все источники. Планировщика нет. Это частично реализованный
бонус, а не автономное поддержание свежести всех данных.

### P2 · Команда: документация и публикация расходятся с локальным состоянием

TASKS.md содержит старые числа, пустой список моделей и TODO для уже сделанного
resolver. Новый compare_parser, его тесты и инструкция ещё локальные изменения,
не вошедшие в опубликованный 44b51c0. Перед сдачей нужны единый README, командный pull,
чистый запуск, визуальный QA и видео. Это не обязанность одного ML-участника.

## Что реально учитывается и что не заявлять

В реестре **18 признаков**, в демо посчитаны 15 hotel-признаков × 25 отелей = 375:
пешеходное расстояние; шумовой proxy и бары; море/закат/горы и минимальные этажи;
авиационная близость/категория; подъёмы и переходы; ночные места и аптека.
Три room-признака — вид на море, закат и шумоизоляция — спрашиваются у отельера.
Учитывается выбранное пользователем и добавленные companions, не все 18 сразу.

Важно:
- 364 значения estimated, 11 unknown; уверенность: 295 low, 69 medium, 11 unknown.
  Наличие значения не равно подтверждённой истинности.
- Вид — расчётный потенциал. Месяцы заката есть в деталях, но даты поездки в поисковой
  схеме не представлены. Нет подбора совместимых фасада/этажа/даты/конкретного номера.
- Шум в ранжировании — proxy и расстояние до условной траектории самолёта. Отдельный
  NoiseModelling-отчёт с дневным/ночным сценарием не является измеренным шумом номера
  и не подключён к ranker. Реальные потоки/треки/звукоизоляция не известны.
- OpenAQ: адаптер есть, ключ не настроен, покрытие Адлера реальными станциями не проверено.
  Измерение ближайшей станции не является измерением у окна и не входит в рейтинг.
- Ночные места — по OSM opening_hours и условию 01:00 во все дни, не по фактической
  дате поездки и не гарантия открытости конкретной аптеки сегодня.
- Погода/климат, GTFS, дети, парковки, питомцы, связь, стройки, цены и доступность
  бронирования не реализованы как полноценные фильтры. Эти примеры необязательны.

По существующим Geo-отчётам: подтверждения вида ограничены малой выборкой, precision
не измерен из-за отсутствия надёжных отрицательных примеров. Фото-проверки: 15/19,
все 4 проверки деревьев не пройдены; три исправления этажности по тем же фото отдельно
исключены из независимых проверок. Это поиск грубых ошибок, не «79% точности вида».

## Твоя зона ответственности как ML

Уже выполнено: адаптер Gemma/Ollama, общий конфиг, промпт, типизированный контракт,
парсер правил для baseline, код ранжирования, комментарии, скрипты метрик и replay,
первый полный замер текущей модели. Обучение собственной нейросети треком не требуется.

Не завершено, в порядке важности:
1. Исправить/защитить обязательность, отрицания, числа и пустой разбор; согласовать
   контракт весов с backend, добавить сквозные проверки найденных ошибок.
2. Проверить разметку человеком; отделить равнозначные ответы от реальных ошибок,
   добавить новые Geo-признаки/числовые цели и отдельный закрытый тест.
3. Проверить формулу и companions: маленький/нулевой вес, отрицательные пожелания,
   неизвестные данные, совместимость номера и фасада.
4. Создать оценку запрос–отель, сравнить v1/v2, сохранить условия и результаты.
5. Передать команде опубликованные скрипты, метрики и ограничения без обещания 95%.

Geo-участник отвечает за источники, корректность георасчётов и проверку реальных фактов.
Backend/Agent — вопросы, БД, API, обновления и интеграцию исправленного контракта.
Frontend — отображение неизвестности/ошибок/слайдеров и визуальное тестирование сайта.
ML проверяет, что исправления сохранили смысл требований и правильное ранжирование;
проверять весь сайт в одиночку тебе не требуется.
