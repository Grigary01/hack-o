# Как проходит запрос

## Online

1. React (`web/src/data/api/source.ts`) посылает `SearchRequest` через `/api`. БД из UI недоступна.
2. `app/api/search.py` принимает **либо** text, **либо** typed parsed, optional weights и `include_simulated=false`.
3. `app/ml/query_parser.py` выбирает provider из конфигурации. Fixture ищет известную формулировку;
   Ollama использует JSON Schema и Pydantic. Отрицания сохраняются, км переводятся в метры.
3a. `app/ml/needs.py` размечает весь запрос на потребности с цитатами; расплывчатое («вид из окна»)
   раскрывается в варианты, а не в вопрос. Ответ по каждому отелю строится по этим потребностям.
4. Неподдерживаемый регион, неясное условие (`unknown_or_ambiguous`) или clarification останавливают поиск
   с `status=needs_clarification`. Темы без признака в реестре (бюджет, бассейн) идут в `unsupported`:
   поиск продолжается по остальному, а гость видит «Не учтено: цена» — ничего не игнорируется молча.
5. `FeatureAgent.ensure` для каждого запрошенного feature выбирает:
   - свежее известное свидетельство → `read_evidence`;
   - отсутствующий Geo-факт → whitelist calculator над локальным snapshot → запись Observation/Evidence;
   - отсутствующий/противоречивый room-факт → `hotelier` → дедуплицированный вопрос;
   - старый/неполный имеющийся Geo-snapshot → `request_snapshot_refresh`, без повторной загрузки и переименования старой даты в новую.
6. Все решения попадают в `trace`: subject, feature, reason, tool_used, result/error. Бюджет — 100 локальных вызовов,
   deadline 20 секунд проверяется **между** вызовами. CPU-вызов принудительно не прерывается;
   граф фиксирован и невелик. HTTP ingest: timeout 120 секунд, 3 попытки; Ollama: 60 секунд, 2 попытки.
7. Repository читает историю. `resolve_feature` исключает будущие, истёкшие и запрещённые demo-источники.
   Несовпадение значений одного subject+feature в перекрывающемся периоде → `conflicted`, value unknown.
8. `rank_hotels` проверяет строгие условия отдельно от мягких. Подтверждённое нарушение hotel-условия → excluded;
   unknown → needs_verification. Оценочные геоданные допускаются с предупреждением и low confidence.
9. Все room-условия проверяются на **одном** номере. Если известные комнаты не подходят, это ещё не доказывает,
   что во всём отеле нет подходящей комнаты: полный inventory неизвестен, отель требует уточнения.
10. `score=sum(w*match)/sum(w_known)`, `coverage=sum(w_known)/sum(w_requested)`, сортировка по score×coverage.
    Нулевые веса исключаются. Без известных мягких фактов score=null. `uncertainty=1-coverage` — доля
    непокрытых пожеланий, не вероятность ошибки. `near=1/(1+d/scale)`, far=1-near; scale в YAML.
11. UI отображает результаты, локальную карту, unknown, исходные наблюдения и warnings. Изменение слайдера
    отправляет тот же parsed query с новыми explicit весами; сами наблюдения не изменяются.

Сохранённый реальный пример: `docs/examples/parse_response.json`, `docs/examples/search_response.json`.

## Диалог

Вопрос дедуплицируется по hotel+feature. Ответ сохраняется отдельно и получает `pending`.
Bounded rules извлекают номера/диапазоны, булево значение, этаж и цитату. Неразобранный остаток
блокирует confirmation. Пользователь принимает или отклоняет весь разбор; частичного молчаливого принятия нет.

Подтверждение выполняется транзакционно: атомарный переход pending → confirmed, Room,
Observation, Evidence, Source и Conflict. Повтор confirmation идемпотентен. Отклонённый ответ нельзя
затем подтвердить: нужен новый ответ. История не перезаписывается.

Все ответы этой версии `hotelier_simulated`. Real search их исключает, demo search использует только
при явном флаге. `estimated` после confirmation означает подтверждённый разбор учебного сообщения,
не независимо проверенное свойство. Факт записан с исходной цитатой и временем.

Политика конфликта — `withhold_and_ask_hotelier`: сохранить обе версии, перестать использовать значение,
попросить уточнение. Автоматической победы «последнего ответа» нет. Административное разрешение спора
с аудитом причины — TODO; пока конфликт прекращает влиять, когда противоречивое свидетельство истекает.

## Offline ingestion

`collect_adler_osm` → bbox из `region.json` → объединённый запрос Overpass → JSON snapshot →
OSMnx walk graph → GraphML и metadata → отбор реальных отелей. Ошибка/remark/пустой ответ не считаются успехом.
Кеш сохраняет запрос и исходную дату; --refresh нужен только для нового сбора.

`compute_geo_features` → проверка доступа/барьеров → кандидаты прохода на пляж →
Dijkstra → noise proxy → `features.json`. `validate_data` повторяет вычисления, сравнивает
**все** наблюдения, проверяет checksum графа и соответствие отелей snapshot.

`seed_demo` валидирует DTO, upsert отелей/definitions, добавляет наблюдения по детерминированному ID.
Существующие ответы/источники сохраняются. Новые противоречивые сведения не заменяют старые.
SQLite runtime не включается в поставку; судья создаёт её одной командой.
