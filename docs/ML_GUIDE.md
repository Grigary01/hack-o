# ML-часть: как читать и менять код

Этот документ предназначен для участника 1 и начинающего разработчика. Комментарии в самих Python-файлах
объясняют назначение блоков, входы, выходы и причины проверок. Здесь те же блоки соединены в один сценарий.

## 1. Что здесь называется ML

Готовая языковая модель нужна для одной задачи: превратить пожелание человека в структурированные условия.
Например, «не дальше 500 метров» → оператор `<=`, число `500`, единица `m`.

Наличие пляжа, длину маршрута и свойства номера модель не устанавливает. Эти сведения приходят из Geo
или подтверждённого разбора ответа отельера. Ранжирование в MVP — прозрачная формула Python, без обучения.

В проекте нет обучения нейросети, BIO-разметки, embeddings, cosine similarity, векторной базы или обученного
рекомендателя. Для текущих числовых и булевых ограничений они не нужны. В режиме `fixture` LLM вообще
не вызывается: это словарь из 12 согласованных текстов и ожидаемых ответов.

3. [`ml/query_parser.py`](../app/ml/query_parser.py): как текст превращается в проверенный объект.
4. [`ml/prompts.py`](../app/ml/prompts.py): какие инструкции и примеры получает модель.
5. [`features/service.py`](../app/features/service.py): какие свидетельства разрешено использовать сейчас.
6. [`ml/ranking.py`](../app/ml/ranking.py): как отсеивать и сортировать отели.
7. [`scripts/evaluate_parser.py`](../scripts/evaluate_parser.py): как измерять ошибки извлечения.
8. [`tests/test_query_parser.py`](../tests/test_query_parser.py), [`test_ranking.py`](../tests/test_ranking.py):

начинать с SQLAlchemy, графов OSM или интерфейса Streamlit.

## 3. Контракт запроса: желания, а не свойства отеля

`ParsedHotelQuery` — Pydantic-модель. Она похожа на строго проверяемый словарь с именованными полями.
`model_validate` принимает словарь, `model_validate_json` принимает JSON-строку, `model_dump` возвращает словарь.
Ошибка проверки означает, что объект нельзя передавать в подбор.

- `region`: поддерживаемая территория. Backend принимает Адлер; другой город вызывает уточнение.
- `hard_constraints`: обязательные условия. Отель с маршрутом 800 м нарушает условие `<= 500`.
- `soft_preferences`: пожелания. «Желательно вид на море» влияет на порядок, но не запрещает другие варианты.
- `unknown_or_ambiguous`: то, что не получилось выразить поддерживаемыми признаками.
- `clarification_question`: вопрос для уточнения.
- `original_text`: реальный исходный ввод для аудита.

`HardConstraint.check_feature` проверяет связи между полями. Для расстояния нужны числовое значение,
единица `m` и scope `hotel`. Входное `.5 km` переводится в `500 m`. `sea_view` — булев признак конкретного
номера, поэтому scope должен быть `room`, а сравнение — `=` или `!=`.

`StrictBool`, `StrictInt` и другие строгие типы защищают от неожиданных преобразований. В Python `True`
ведёт себя как число 1, но «1 метр» и «да» в нашей предметной области различны. Неизвестные поля,
отрицательные расстояния, неизвестные ключи, `NaN` и бесконечность отклоняются.

`SoftPreference.importance` — пользовательский приоритет от 0 до 1. Это **не уверенность LLM** и не
обучаемый параметр модели. `weight_source` показывает происхождение:

- `default`: вес берётся из YAML, даже если LLM прислала другое число;
- `explicit`: пользователь задал число или изменил ползунок;
- `relative_inferred`: интерпретация фразы вроде «тишина важнее вида».

`unique_preferences` запрещает повтор мягкого признака: иначе он мог бы получить двойной вес случайно.
Для hard допустимы два ограничения на один признак, например `>= 100` и `<= 500`.

## 4. Парсеры и выбор режима

`QueryParser` — интерфейс `parse(text) → ParsedHotelQuery`. `Protocol` описывает этот интерфейс без
привязки к реализации. Многоточие в его методе — нормальное объявление интерфейса, не незаконченный код.
`make_parser` выбирает реализацию из `PARSER_MODE` при запуске backend.

### FixtureQueryParser

В конструкторе загружается `data/demo/query_fixtures.json`. `normalize` убирает регистр, лишние пробелы
и конечную пунктуацию, но сохраняет числа, слова и отрицания. Затем выполняется точный поиск в словаре.
Найденный JSON проходит тот же контракт, что и ответ LLM. Неизвестный текст требует уточнения.

Это даёт демонстрацию без GPU, модели и сети, а также позволяет воспроизвести ошибки остальных модулей.
Добавление одного fixture не улучшает понимание произвольного русского текста. Кнопка примеров в UI
показывает поддерживаемые формулировки, чтобы это ограничение было видно пользователю.

### OllamaQueryParser

1. `ParsedHotelQuery.model_json_schema()` строит описание JSON автоматически из Python-классов.
2. В поля `feature_key` добавляется `enum` из актуального YAML-реестра.
3. `query_messages` готовит инструкции, примеры и пользовательский ввод.
4. HTTP POST `/api/chat` передаёт `format=schema`, `stream=False`, `options.temperature=0` и ограничение вывода.
5. `raise_for_status` отбрасывает HTTP-ошибки. `model_validate_json` проверяет содержимое ответа.
6. `original_text` заменяется реальным вводом, чтобы модель не могла переписать историю запроса.
7. При ошибке есть одна повторная попытка. После двух неудач API возвращает понятную ошибку 502.

Схема помогает получить корректную **форму**, но не гарантирует правильный **смысл**. Модель может
вернуть допустимый `>=`, неверно прочитав «не дальше». Это обнаруживается gold-набором и метриками.
`temperature=0` уменьшает случайность, но также не доказывает правильность.

HTTP-клиент подменяется в тестах на `httpx.MockTransport`. Так проверяются запрос, JSON Schema, обработка
ошибок и ограниченные повторы. Ответ такого теста написан нами; это не оценка самой модели.

## 5. Промпт и few-shot

`query_messages` создаёт system-сообщение с правилами предметной области и актуальным реестром признаков.
Затем идут восемь пар «user-текст / assistant-JSON» из demo, а последним — новый запрос.
Это называется few-shot: примеры находятся в контексте вызова, веса модели не обучаются.

Правила объясняют операторы, отрицания, метры, обязательность, room/hotel, веса и уточнения.
«Недалеко от моря» без числа означает мягкое `near`; модель не должна придумывать 500 метров.
«До 5000 рублей» сейчас требует уточнения, потому что цены не подключены.

32 held-out примера из `queries_gold.jsonl` не читаются этим модулем. Если использовать их ответы в промпте,
метрика перестанет показывать перенос на новые формулировки. После многократной настройки по held-out
нужно собрать новый независимый финальный набор.

## 6. Откуда берётся значение признака

Ранжировщик вызывает `resolve_feature`, а не выбирает последнее наблюдение самостоятельно.
Функция отбирает нужный `subject_id + feature_key`, исключает симуляцию по умолчанию, будущие и истёкшие
наблюдения. Если действующие значения противоречат друг другу, значение возвращается как неизвестное.

Различайте:

- `False`: известно, что свойства нет;
- `0`: известно нулевое расстояние;
- `None`: подходящего текущего значения нет;
- `status`: причина/качество значения (`estimated`, `unknown`, `stale`, `conflicted` и т. д.).

Поэтому в коде используется `is None`, а не `if not value`. Второй вариант ошибочно смешал бы эти случаи.
История наблюдений сохраняется в объяснениях и может быть показана пользователю.

## 7. Ранжирование по блокам

### soft_match: один признак → степень соответствия

Для желания быть ближе: `near = 1 / (1 + distance / scale)`. Если `scale=1000`, расстояния 0, 1000 и 2000 м
дадут 1, 0.5 и примерно 0.333. `scale` — характерный масштаб из YAML, а не максимальная допустимая дистанция.
Для `far` используется `1 - near`. Булевы значения сравниваются с желанием, в том числе с `desired=False`.
Тишина high/medium/low получает 1/0.5/0: это явно заданная эвристика, не акустическое измерение.

### rank_variant: отель + один номер

Блок A проверяет каждое hard-условие через разрешённый оператор из `OPS`. Здесь нет `eval` пользовательского
текста. Результат каждого сравнения — `True`, `False` или `None`. Нарушение обязательного расстояния нельзя
компенсировать хорошим видом.

Блок B проходит по мягким пожеланиям. Нулевой вес полностью выключает пожелание. Известное значение
даёт `weight × match`; неизвестное остаётся в общей сумме запрошенных весов, но не в сумме известных.

Блок C возвращает три числа:

```text
score         = сумма(weight × match) / сумма известных весов
coverage      = сумма известных весов / сумма всех активных весов
ranking_score = score × coverage
```

Если ни одного мягкого значения нет, `score=None`. Если активных мягких пожеланий нет, `coverage=0`:
мягкое ранжирование не используется, порядок определяется стабильным ID. `uncertainty=1-coverage` — доля
непокрытых пожеланий, **не вероятность ошибки** и не измеренная статистическая уверенность.

Любой hard `False` даёт `eligible=False`. Если нарушений нет, но есть `None`, получаем `eligible=None`.
Если все обязательные условия выполнены или их нет, `eligible=True`. Оценочные факты сопровождаются предупреждением.

### rank_hotels: варианты номеров и итоговые группы

Для room-пожеланий каждый известный номер проверяется отдельно. Нельзя соединить вид из 301 с шумоизоляцией
302 и назвать это подходящим номером. Сначала выбирается лучший допустимый вариант внутри отеля, затем
отели раскладываются в `matched`, `needs_verification`, `excluded`.

Неподходящие известные номера не доказывают отсутствие подходящих неизвестных: полного inventory нет.
Поэтому только из-за такого room-случая весь отель не исключается, а отправляется на уточнение.
Внутри каждой группы сортировка идёт по `ranking_score`, затем `coverage`, затем стабильному OSM ID.

## 8. Один реальный запрос от начала до конца

Ввод: «Ищу тихий отель в Адлере, не дальше 500 метров пешком от пляжа, хотелось бы вид на море».
Полные ответы сохранены в [parse_response.json](examples/parse_response.json) и
[search_response.json](examples/search_response.json). Они получены вызовом API на чистой seed-базе.

Парсер возвращает hard `walking_distance_to_beach_m <= 500 m`, soft `quietness_proxy=high` с весом 0.9
и soft `sea_view=True` для номера с весом 0.6. Геоданные уже лежат в SQLite после seed;
агент читает evidence и создаёт вопросы отельеру для отсутствующего вида.

У первого результата `osm:node:10058556917` оценочный маршрут 319.8 м, quietness proxy high, вид неизвестен.
Название объекта в OSM — «Островок»; это не свидетельство связи с сервисом организатора.

```text
hard:     319.8 <= 500 → True
тишина:   match = 1, известный вес = 0.9
вид:      unknown, запрошенный вес = 0.6
score:    0.9 × 1 / 0.9 = 1
coverage: 0.9 / (0.9 + 0.6) = 0.6
порядок:  1 × 0.6 = 0.6
```

Итого: 12 `matched` по имеющимся оценкам, 2 требуют уточнения, 11 нарушают строгий порог.
`score=1` здесь не означает «идеальный отель»: неизвестны 40% веса пожеланий, а геооценки имеют low confidence.
Если заменить желательный вид обязательным, отсутствие вида станет hard unknown и потребует уточнения.

## 9. Ответ отельера — соседняя задача извлечения

[`hotelier/dialogue.py`](../app/hotelier/dialogue.py) использует отдельный ограниченный rule-based extractor.
Он читает номера/диапазоны, алиасы булевого признака из YAML, отрицание и этаж. Это не Ollama и не универсальный
анализатор русского языка. Сложные условия и неразобранные части блокируют подтверждение; все распознанные
записи всё равно показывает человеку до сохранения.

«В номерах 301–305 вид на море, все на 3-м этаже» даёт пять room-specific claims, а не одно свойство всего отеля.
После подтверждения запись остаётся `hotelier_simulated`, `estimated`, с исходной цитатой. Она участвует только
в поиске с явным флагом симуляции. Другой ответ не стирает первый: противоречия сохраняются и блокируют значение.

## 10. Метрики: что считает evaluator

44 запроса и ожидаемые JSON созданы coding assistant: 12 demo и 32 held-out. Это синтетический набор, а не независимая ручная gold-разметка; человеческий пересмотр ещё нужен.
`measure` вызывает настоящий выбранный parser для каждого текста и сравнивает с эталоном.

- `exact_match`: доля полностью равных контрактов, включая регион, веса, порядок списков и текст уточнения.
  Семантически похожая перефразировка уточнения может не пройти эту строгую проверку.
- `field_precision`: сколько из выданных hard/soft полей верно.
- `field_recall`: сколько из ожидаемых hard/soft полей найдено.
- `field_f1`: гармоническое среднее precision и recall. Регион и clarification проверяет exact match,
  они не входят в field-метрику.
- `dimensions`: отдельные совпадения операторов, чисел и поддержанных паттернов отрицаний.
- `covered`: parser не отказался из-за отсутствия fixture/ошибки; это не доля правильных ответов.
- `errors`, `mismatches`: причины сбоев и пары expected/actual для ручного разбора.

`fields` превращает поля в мультимножество `Counter`. Пересечение даёт TP, лишнее в ответе — FP,
недостающее относительно gold — FN. Неверный оператор одновременно даёт один FP и один FN.
`canonical` считает `500` и `500.0` одним числом, сохраняя различие `False` и `0`.

Реальный прогон fixture: demo 12/12, exact-match=1 и field-F1=1; held-out покрытие 0/32, exact-match=0 и F1=0.
Это ожидаемая граница словаря, **не качество языковой модели**. Реальная Ollama здесь не запускалась.

```bash
python -m scripts.evaluate_parser --mode fixture
# После отдельной установки/запуска Ollama и загрузки модели:
python -m scripts.evaluate_parser --mode ollama
```

Второй запуск запишет отдельный `parser_metrics_ollama.json` с фактически использованным именем модели,
временем, ошибками и несовпадениями. Нельзя публиковать результат fixture как результат Gemma.

## 11. Как безопасно изменить ML-часть

Изменение веса команды → `registry.yaml`. Пользовательские веса → слайдер или поле `weights` API.
Новая формулировка для офлайн-демо → `query_fixtures.json`, без обещаний универсального понимания.
Улучшение понимания свободного текста → `prompts.py` и измерение на отдельном наборе.
Новый признак → сначала тип/scope/provider в реестре и реальный источник, затем примеры и тесты.

Не записывайте свойства отеля из пожеланий человека. Не превращайте unknown в False или хороший score.
Не подменяйте пешеходный маршрут прямой линией. Не используйте `confidence` LLM как статистическую вероятность.

Для самостоятельного разбора сначала воспроизведите пример выше, затем измените вес вида на 0, сделайте вид
обязательным, подтвердите симулированный ответ для 301 и добавьте противоречащий ответ. Для каждого шага
посмотрите JSON, coverage, группу результата и evidence. Эти четыре изменения хорошо показывают границы модулей.
