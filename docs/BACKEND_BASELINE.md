## Сценарий через настоящий HTTP и SQLite

Использована отдельная постоянная база `runtime/backend_baseline.db`:

```bash
DATABASE_URL=sqlite:///runtime/backend_baseline.db PARSER_MODE=fixture DEMO_MODE=true \
  .venv/bin/python -m scripts.seed_demo --environment

DATABASE_URL=sqlite:///runtime/backend_baseline.db PARSER_MODE=fixture DEMO_MODE=true \
  .venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 18000

# Во втором терминале:
API_URL=http://127.0.0.1:18000 .venv/bin/python -m streamlit run frontend/app.py \
  --server.address 127.0.0.1 --server.port 18501 --server.headless true \
  --browser.gatherUsageStats false
```

Фактические результаты:

1. Backend health: `status=ok`, `database=ok`, 25 отелей, parser `fixture`.
   Streamlit health: `ok`. Никакие внешние сервисы health не выдаёт за проверенные.
2. Первый пример запроса вернул 12 `matched`, 2 `needs_verification`, 11 `excluded`.
   Использованы настоящие часы, без подмены даты snapshot.
3. Для отеля `osm:node:10058556917` создан вопрос о `sea_view`. Ответ
   «В номере 301 есть вид на море, на 3-м этаже» сохранён как `pending`;
   до подтверждения наблюдение не появилось.
4. Подтверждение создало одно наблюдение. Повторное подтверждение вернуло
   `idempotent=true`, не создало дубликат.
5. Запрос «Нужен номер обязательно с видом на море» дал 0 совпадений в обычном
   режиме и 1 совпадение при `include_simulated=true`.
6. Подтверждён противоположный ответ о том же номере. Возник один конфликт,
   обе версии сохранились, демо-поиск снова вернул 0 совпадений.
7. Streamlit AppTest прошёл экран поиска, создание вопроса, разбор и подтверждение

   Транспорт API не подменялся. Подтверждение появилось в состоянии интерфейса.
8. Сервер остановлен и запущен заново с той же SQLite. Через HTTP подтверждено
   сохранение исходных противоречащих наблюдений, конфликта и вопроса.

После сценария в отдельной базе: 25 отелей, 6 номеров, 82 наблюдения,

## Известные пробелы и ограничения

- После появления конфликта и повторного поиска вопрос остался `answered`.
  Это подтверждённый пробел жизненного цикла; исправление запланировано отдельно.
- В OpenAPI отсутствует ручка решения конфликта. На этапе 2 нужно добавить
  хранение решения и его применение во всех потребителях текущего знания.
- Браузерная визуальная проверка недоступна: инвентарь CUA не содержит браузеров
  или приложений; native pipe не запускается. AppTest подтверждает выполнение
  UI-сценария, но не внешний вид страницы в браузере.
- Во время AppTest Streamlit предупредил об одновременном задании начального
  значения слайдера и его значения через Session State. Сценарий прошёл;
  предупреждение можно устранить при работе над frontend.
- Результаты реального свободного текста не проверены: используется `fixture`.

## Контракты для следующих этапов

Сохраняются действующие URL, `ReplyExtraction`, `ranking_method`, `balance`,
`include_simulated`, три группы поисковой выдачи и разделение по конкретным
номерам. Сохраняются исходные даты, TTL, уверенность и признак симуляции.

Проект нового действия: `POST /api/hotelier/conflicts/{conflict_id}/resolve`,
поля `selected_observation_id` и непустой `reason`. Одинаковое повторное решение
идемпотентно; несовместимое повторное действие — 409. Чужое наблюдение — 422;
отсутствующий объект — 404. Это проект контракта, ещё не реализованный API.
Обозначение оператора в локальном симуляторе формируется на backend.

Обработчик ответа отельера будет принимать `feature_key` и `text`, возвращать
существующий `ReplyExtraction`. Идентификаторы отеля и вопроса поступают из БД.
Стороннее согласование с участниками команды в этой сессии не проводилось.

Следующее изменение: этап 2 [плана](BACKEND_CHANGE_PLAN.md) — миграции,
решения конфликтов и единое применение решения в агенте, поиске и evidence.
