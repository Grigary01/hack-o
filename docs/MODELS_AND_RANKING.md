## Облачная альтернатива

Backend и интерфейс остаются на ноутбуке, а LLM вызывается через **Groq Free Plan**.
Модель не нужно скачивать, покупать GPU или размещать свой inference-сервер.
Это не публикация всего приложения в интернете: для общей ссылки команде или
жюри отдельно нужен доступ к приложению/хостинг. Локальный backend на ноутбуке
годится для презентации; облачная LLM снимает именно нагрузку на его память.

1. Зарегистрироваться на https://console.groq.com/keys, выбрать Free Plan.
2. В локальном `.env` указать:

```dotenv
PARSER_MODE=groq
GROQ_API_KEY=your-private-key
```

3. Перезапустить backend. Ключ не коммитить и не передавать через frontend.
Текст запроса и два примера будут отправляться Groq; база отелей не отправляется.

28 октября на Mac установлена Gemma 12B (8.2 GB), выполнены два реальных smoke-запроса.
Полного сравнения моделей на gold пока нет. Облачные кандидаты требуют отдельного
`GROQ_API_KEY`; наличие профиля не означает, что генерация проверена. Имя облачной
модели задаётся полем `groq_model` в общем YAML.

Кандидаты в `data/evaluation/model_candidates.json`:

- `groq-20b`: `openai/gpt-oss-20b`, 21B параметров всего / 3.6B активных;
- `groq-120b`: `openai/gpt-oss-120b`, 117B всего / 5.1B активных (название семейства 120b);
- `groq-qwen27b`: `qwen/qwen3.8-27b`, альтернативный облачный кандидат;
- локальные резервные профили: Gemma3 12B, Qwen3 14B, Gemma3 27B.

120B — не гарантия лучшего извлечения русских условий, особенно отрицаний/чисел.
MoE использует часть параметров на токен; общее число и активное число различаются.
На Mac 24 GiB Gemma 27B (~17 GB весов) оставляет мало места системе и контексту,
поэтому этот профиль — эксперимент, не основной рекомендуемый путь.

У Groq есть бесплатные квоты. На момент проверки для GPT-OSS указаны 30 RPM,
1000 RPD, 8000 TPM, 200000 TPD. Точная квота зависит от аккаунта и может меняться;
на платном аккаунте тот же ключ не становится бесплатным из-за нашего кода.
Приложение не включает платный план, не покупает кредиты и не переключает модель
при ошибке квоты. Доступность из региона пользователя не проверена; ошибки
401/403/429/сети показаны явно. Это не безлимитный бесплатный сервис.

## Воспроизводимое сравнение моделей

```bash
# Preflight: доступность /models или /api/tags, без генерации и без скачивания.
python -m scripts.benchmark_models

# Сначала маленький smoke после добавления ключа:
python -m scripts.benchmark_models --profiles groq-20b groq-120b groq-qwen27b --run --limit 3

# Затем все 32 проверочных запроса, отдельно от demo:
python -m scripts.benchmark_models --profiles groq-20b groq-120b groq-qwen27b --run
```

По умолчанию пауза 60 секунд между запросами, чтобы не исчерпывать бесплатную
TPM-квоту; опция `--interval` позволяет настроить её по реальной квоте. JSON-schema
передаётся провайдеру; prompt больше не дублирует её и использует два demo-примера.
Для всех кандидатов одинаковые текст, примеры, схема и набор проверок. Разные
провайдеры могут иметь разные механизмы декодирования, это не сравнение чистых весов.

Отчёт `runtime/model_comparison.json`: точные имена моделей, SHA256 dataset/prompt/
schema, наличие модели, ответы каждого запроса, ошибки, exact-match, field precision/
recall/F1, числа/операторы/отрицания, median и p95 полной задержки. Неудачи остаются
в знаменателе. Промежуточный результат сохраняется после каждого запроса.
В preflight никаких фиктивных метрик нет. Победитель автоматически не назначается.

**Происхождение 44 запросов:** они и ожидаемые JSON созданы coding assistant,
это синтетические тестовые случаи, не реальные запросы пользователей и не
независимая ручная gold-разметка. 12 demo / 32 held-out; только первые 2 demo
попадают в prompt. Перед выводами о качестве нужен человеческий пересмотр и
отдельный закрытый тестовый набор. Новые utility-кривые покрыты unit-тестами,
но в старых 44 запросах почти нет подобных формулировок — набор нужно расширить.

## Почему hard/soft остаётся, но этого недостаточно для оценки

Обязательность — отдельное измерение запроса. «Не дальше 500 м» нельзя нарушить
ради красивого вида. Условие hard сохраняет три результата: подходит / нарушено /
неизвестно. Неизвестный обязательный факт по-прежнему требует проверки.

Способ измерить удовлетворённость — другое измерение. Для мягкого расстояния
можно задать идеальное значение, допустимое отклонение или целевой диапазон.
Одна фича может иметь hard-границу и отдельную soft-цель одновременно.

Пример: «Не дальше 700 м; идеально до 200 м, к 600 м становится неудобно»:

```json
{
  "hard_constraints": [{"feature_key":"walking_distance_to_beach_m","operator":"<=","value":700,"unit":"m","scope":"hotel"}],
  "soft_preferences": [{"feature_key":"walking_distance_to_beach_m","desired":"near","importance":0.8,"weight_source":"explicit","scope":"hotel","utility":{"kind":"lower","ideal_min":null,"ideal_max":200,"tolerance":400}}]
}
```

Удовлетворённость: 200 м → 1; 400 м → 0.5; 600 м → 0. При 650 м hard выполнен,
но мягкое пожелание не выполнено. `higher` работает наоборот; `target_range`
даёт 1 внутри идеального диапазона и линейное снижение снаружи. Это математика
предпочтений, не физическая модель. В частности, дБ — логарифмическая физическая
величина; функция полезности по дБ не должна называться сложением источников шума.
LLM не придумывает tolerance. Без явной цели применяется прежняя функция near/far.

## Группы, баланс и неизвестность

Связанные признаки группируются: тишина/удалённость от баров/шумоизоляция →
«Тишина и сон»; море/закат → «Вид из номера»; путь до пляжа → «Доступ к пляжу».
Пожелание находиться **рядом** с барами относится к развлечениям, не к тишине.
Это явная предметная политика, а не статистически доказанная корреляция.

Внутри группы полезности усредняются с пользовательскими весами. Вес группы
равен максимальному весу входящих пожеланий. Поэтому добавление копии сигнала
о тишине не удваивает автоматически важность тишины относительно пляжа.

```text
F = (1 - balance) × weighted_mean(group_utilities)
    + balance × min(group_utilities)
```

По умолчанию balance=0.25. При равной средней оценке [0.5,0.5] предпочтительнее
[1,0]: один провальный аспект не полностью компенсируется другим. Никакой
штраф не отменяет обязательное ограничение. balance — параметр нашей политики,
а не вероятность или обученный коэффициент; его надо проверять с пользователями.

Неизвестная мягкая полезность задаётся диапазоном [0,1]. Считаются нижняя и верхняя
границы F; порядок консервативный — по нижней. Интервал **не доверительный**:
он не учитывает погрешности известных оценочных признаков. Источники и их
ограничения остаются видимыми. coverage — доля известных пожеланий с учётом групп,
score — соответствие известных пожеланий, ranking_score — итоговая нижняя F.

Полностью известные варианты получают метку Парето, если есть другой вариант
не хуже по всем пожеланиям и лучше хотя бы по одному. Неизвестные обязательные
условия не дают такую метку; отели из выдачи из-за неё не удаляются.

В UI переключатель `balanced_v2` / `weighted_v1`. API SearchRequest принимает
`ranking_method` и `balance` (0..1). v2 — default API/UI; прямой вызов rank_hotels
сохраняет default v1 для совместимости. Проверяются hard/no-compensation,
монотонность полезности, целевые диапазоны, unknown-интервалы, группировка,
равный средний score при разном балансе. Нет обучения на синтетических оценках.
