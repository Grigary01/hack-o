# Этап 3: жизненный цикл вопросов

> 29.10.2026 Streamlit (`frontend/`) удалён; интерфейс — React в `web/`. Упоминания Streamlit/AppTest ниже — история проверок того времени.


На пару `(hotel_id, feature_key)` по-прежнему хранится один вопрос. Его `id`,
`created_at`, исходный текст и все ответы сохраняются. Меняются текущие
`status`, `context` и `updated_at`; повторное открытие не создаёт новый вопрос.

## API для frontend

```text
GET /api/hotelier/questions
GET /api/hotelier/questions?hotel_id=...&status=open
GET /api/hotelier/questions?hotel_id=...&status=answered
POST /api/hotelier/questions
```

Тело POST осталось прежним: `hotel_id`, `feature_key`. Существующие поля ответа
`id`, `hotel_id`, `feature_key`, `text`, `status`, `created_at` сохранены.
Новые поля описаны моделью `HotelierQuestion` в `app/schemas/hotelier.py`:

```json
{
  "context": {
    "reasons": ["conflicted"],
    "subject_ids": ["osm:node:123:room:302"],
    "review_answer_id": "ID последнего отправленного разбора"
  },
  "updated_at": "2026-10-28T20:00:00+00:00"
}
```

Это иллюстрация добавляемых полей. Полные ответы настоящего API сохранены в
[question_integration_fixture.json](examples/question_integration_fixture.json).

Статусы вопроса не изменились: `open` и `answered`. Они отличаются от статусов
ответа: `pending`, `confirmed`, `rejected`. Значение свойства `false` — известное
отрицание, поэтому само по себе не требует повторного вопроса.

| `context.reasons` | Причина открытого вопроса |
|---|---|
| `unknown` | Нет пригодного значения по вопросу или нужному номеру |
| `stale` | Свидетельства устарели; решение конфликта не продлевает TTL |
| `conflicted` | Осталось неразрешённое или новое противоречие |
| `pending_answer` | Последний отправленный разбор ожидает решения |
| `unparsed_answer` | В последнем черновике есть неразобранный текст |
| `rejected_answer` | Последний разбор отклонён, требуется новый ответ |

Причин может быть несколько. `subject_ids` содержит номера с нерешённым
уточнением или ожидающим рассмотрения разбором. Пустой список допустим:
например, при общем вопросе без известных номеров или неразобранном тексте.
У закрытого вопроса причины и список нужных номеров пусты.

`review_answer_id` указывает именно на последний отправленный разбор. Он не
вычисляется по UUID или порядку строк с одинаковым временем. Обработка старого
черновика не отменяет более поздний подтверждённый ответ. Неизвестные номера,
которые уже были включены в уточнение, остаются в нём до получения данных.

Новые факты, подтверждение/отклонение ответа и решение конфликта пересчитывают
вопрос в той же транзакции. При ошибке откатываются факты и состояние вопроса.
Неподтверждённый или неоднозначный ответ не создаёт пригодного для поиска факта.

TTL может истечь без записи новых данных. Поэтому очередь пересчитывается при
чтении и поиске; фильтр `status` применяется после пересчёта. Отдельного фонового
таймера нет. `updated_at` меняется при изменении состояния/контекста, а не при
каждом одинаковом чтении. `created_at` остаётся прежним.

Локальная очередь учитывает подтверждённые симулированные ответы. Обычный поиск
по-прежнему их исключает, но переключение `include_simulated=false` само по себе
не открывает повторно выполненный демо-вопрос. Список `pending_hotelier_question_ids`
больше не включает закрытый вопрос, возвращённый повторным вызовом инструмента.

Фильтры ошибок: неизвестный `hotel_id` — 404, неверный `status` — 422.
Сохраняется ограничение `DEMO_MODE`; при его отключении кабинет возвращает 403.

## Подключение экрана

React (`web/src/data/api/source.ts`) использует очередь так:
`GET /api/hotelier/questions?hotel_id=&status=` — список с `context` (почему вопрос открыт),
`POST /api/hotelier/questions/{id}/answer` → `GET /api/hotelier/answers/{id}` (проверка разбора)
→ `POST /api/hotelier/answers/{id}/confirm` с `accept: true|false`.

Снимки состояний очереди для разработки экрана без сервера: сценарии `open`, `pending`, `answered`,
`reopened`, `resolved`, `unparsed`, `rejected`, `stale` в
[question_integration_fixture.json](examples/question_integration_fixture.json). Это снимки контракта,
а не альтернативный backend; отправку и подтверждение ответов они не подменяют.

Обновить снимки можно командой `python -m scripts.export_question_contract`.
Она использует отдельную базу и `FixtureQueryParser`, без настоящей LLM.

## Граница ML

`ParsedHotelQuery`, `ReplyExtraction`, формат `claims/unparsed` и подтверждение
остались прежними. ML возвращает разбор; backend определяет состояние вопроса
по пригодным наблюдениям и результату рассмотрения ответа. Статус вопроса
не нужно вычислять в модели. Заменяемый обработчик ответа реализован в backend-части
этапа 4: [контракт и настройка](REPLY_PARSER_INTEGRATION.md). Реальная генерация
и качество модели пока не проверены.

## Миграция и проверки

Перед запуском старой базы: `python -m scripts.migrate_db`.
Версия `0003_question_lifecycle` добавляет `context` и `updated_at`, заполняет
их по существующим вопросам/последним ответам. Она не удаляет и не пересоздаёт
вопросы, ответы, наблюдения или решения. Для базы версии 0002 структура также
проверяется перед обновлением; создаётся резервная копия.

Проверено: **112 passed, 1 skipped** (внешний NoiseModelling). Полный набор
включает прежние проверки frontend и ML. Отдельно выполнен настоящий HTTP-прогон
через оба frontend-клиента на копии заполненной базы этапа 2, с перезапуском
backend и запуском существующего Streamlit через AppTest с настоящим HTTP.
Один вопрос сохранил идентификатор и шесть ответов, включая отклонённый.
Проверены откат транзакции, истечение TTL, другие номера и порядок черновиков.

Отчёты: [Pytest](examples/backend_stage3_pytest.xml),
[HTTP и сохранение истории](examples/backend_stage3_flow.json),
[воспроизводимость геоданных](examples/backend_stage3_data_validation.json).

Визуальный браузерный QA и качество реальной ML-модели не заявляются.
