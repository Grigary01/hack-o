# Обновление SQLite

Миграции Alembic находятся в `migrations/`; текущая версия —
`0003_question_lifecycle`. Историческая схема `cad3003` зафиксирована отдельно
в `legacy_schema.sql` и не зависит от текущих ORM-моделей.

## Команда

Остановите приложение, установите обновлённые зависимости и выполните из корня:

```bash
source .venv/bin/activate
python -m pip install -c requirements.lock -e '.[test]'
python -m scripts.migrate_db
```

Для другой базы:

```bash
python -m scripts.migrate_db --database-url sqlite:///runtime/another.db
```

Настройка по умолчанию берётся из `DATABASE_URL`, как и у backend.

## Что происходит

1. Для существующей непустой SQLite создаётся новая резервная копия рядом
   с базой в `backups/`, без перезаписи старых копий. Выполняется `integrity_check`.
2. Для базы без версии проверяются таблицы, колонки/типы/nullability,
   первичные/внешние ключи, уникальность и индексы. Распознаются только точные
   известные схемы: исходная `0001_baseline`, схема этапа 2 и текущая схема.
   Неизвестная структура отклоняется до присвоения версии и изменения данных.
3. Пустая база получает исходную схему и миграцию. Известная старая база получает
   версию исходной схемы, новую таблицу `conflict_resolutions` и контекст вопросов
   (`context`, `updated_at`). Таблицы отелей, номеров, вопросов, ответов,
   наблюдений и отчётов среды не пересоздаются. Из версии 0002 применяется
   отдельная миграция 0003 с сохранением решений и заполнением контекста.
4. Действия выполняются с явным `BEGIN IMMEDIATE`: прерывание откатывает
   присвоение версии и DDL. Повторный запуск уже обновлённой базы безопасен.

Вывод команды содержит `revision` и путь `backup` (либо `null` для новой базы).
При старой версии backend останавливается с инструкцией запустить миграцию;
существующая база не обновляется скрыто при старте. Для совершенно пустой базы
`create_db()` по-прежнему обеспечивает создание схемы.

Используйте wrapper `python -m scripts.migrate_db` для обновления: голая команда
`alembic upgrade head` намеренно не обходит проверку и резервную копию.
Автоматическое удаление истории через downgrade не поддерживается.

Перед восстановлением остановите процессы и сохраните текущий файл отдельно.
Путь резервной копии возвращает команда; для чтения копии можно задать отдельный
`DATABASE_URL`, не заменяя рабочую базу.

## Проверки

`tests/test_migrations.py` проверяет пустую и заполненную старую базу, точное
сохранение прежних полей всех существующих таблиц и резервной копии, повторное обновление,
отказ для неизвестной схемы и откат DDL при ошибке. Контроль текущей схемы также
сравнивает миграции с ORM-моделями.

Дополнительно обновлена копия настоящей базы этапа 1: сохранились 25 отелей,
6 номеров, 82 наблюдения, 25 вопросов, 3 ответа, 1 конфликт и 27 отчётов среды.
`integrity_check` и `foreign_key_check` пройдены. Исходная база и её резервная
копия этапа 1 сохранены. Результат: [HTTP-прогон](examples/backend_stage2_flow.json).

Передача одной connection в программные команды следует
[документации Alembic](https://alembic.sqlalchemy.org/en/latest/cookbook.html#sharing-a-connection-across-one-or-more-programmatic-migration-commands).

Этап 3 дополнительно проверяет откат после добавления первой колонки и обновление
заполненной базы версии 0002 с сохранением решений и последних черновиков.
Настоящий HTTP-прогон на копии базы этапа 2: [отчёт](examples/backend_stage3_flow.json).
