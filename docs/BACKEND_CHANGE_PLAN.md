## Область работ и исходное состояние

В `hack_0` находится один репозиторий: `hack-o`. Все пути далее указаны
относительно него. Работать в корневых `app/`, `frontend/`, `scripts/`, `tests/`
и `docs/`. Вложенная `Островок/` была старой копией; после приёмки удалена
29.10.2026 по запросу владельца. Единственная рабочая реализация находится в корне.

По чтению кода и JSON уже имеются:

- FastAPI, SQLAlchemy/SQLite, Pydantic, HTTP-клиент Streamlit.
- 25 отелей, 75 геонаблюдений, 12 подготовленных формулировок запроса.
- Выбор существующего факта, геоинструмента или вопроса отельеру.
- Источники, даты, TTL, история наблюдений, обнаружение противоречий.
- Предварительный разбор ответа, ручное подтверждение, защита от повторного
  подтверждения и транзакция на HTTP-операцию.
- Совместная проверка свойств одного номера, разделение реальных и
  симулированных фактов, несколько методов ранжирования.

Подтверждённые пробелы:

| Область | Что сейчас | Что требуется |
|---|---|---|
| Конфликты | `ConflictRow` хранится, `resolve_feature()` блокирует разные значения | Явное решение, которое одинаково учитывают поиск, агент и evidence |
| Вопросы | `ensure_question()` возвращает старую запись; подтверждение безусловно ставит `answered` | Повторное открытие при конфликте/устаревании и корректное закрытие |
| Ответ отельера | `submit_answer()` напрямую вызывает regex-функцию | Заменяемый parser с проверкой контракта на backend |
| API | Часть ручек возвращает словари без `response_model` | Явные схемы и согласованные ошибки |
| Свободный запрос | По умолчанию `fixture`; адаптеры Ollama/Groq существуют | Проверенный сценарий с новой формулировкой на реальной модели |
| Новая характеристика | `blackout_curtains` есть только во временном реестре теста | Полная проверка добавления через реестр вплоть до поиска |
| Схема БД | Используется `create_all()` | Версионированное обновление существующей базы с сохранением истории |

Приложение и тесты при составлении плана не запускались. В доступном Python 3.12
не установлены `pytest`, `fastapi` и `sqlalchemy`; локальной `.venv` нет.
Это ограничение проверки, а не установленная ошибка проекта.

## 2. Реализовать решение конфликтов и обновление схемы

Файлы: `app/storage/models.py`, `app/storage/repository.py`,
`app/storage/db.py`, `app/features/service.py`, `app/schemas/hotelier.py`,
`app/api/hotelier.py`, `app/agent/feature_agent.py`, `app/ml/ranking.py`,
`app/api/hotels.py`. Новые: `migrations/`, при выборе Alembic — `alembic.ini`.

1. Добавить `ConflictResolutionRow`: идентификатор конфликта, выбранного
   наблюдения, причина, время, обозначение оператора. Исходные наблюдения и
   конфликт не менять и не удалять. Для первого варианта — одно решение на
   конфликт с уникальностью по `conflict_id`.
2. Подготовить миграции вместе со схемой: исходная версия и обновление.
   Учесть как чистую БД, так и существующую, созданную через `create_all()`.
   Присваивать ей исходную версию только после проверки фактической схемы.
   Alembic — предлагаемый механизм; зависимость и команду добавить в проект.
3. Добавить `POST /api/hotelier/conflicts/{conflict_id}/resolve` с телом
   `{selected_observation_id, reason}`; локальное действие ограничить `DEMO_MODE`.
   Оператора для симулятора обозначать на сервере, не выдавать это за авторизацию.
4. Проверять непустую причину и принадлежность выбранного наблюдения обеим
   сторонам конфликта по ID: оно должно быть одной из них и относиться к тому же
   отелю, номеру и признаку. Отсутствующий объект — 404, неверный выбор — 422.
   Одинаковое повторное решение идемпотентно; несовместимое — 409.
5. Сделать единое вычисление текущего знания в `resolve_feature()` с учётом
   решений. Передать необходимые конфликты/решения во все вызовы, включая обе
   ветви `current_real`/`current_demo` в evidence. Загрузку выполнить на уровне
   репозитория/вызывающего сервиса, не добавлять скрытые SQL-запросы в resolver.
6. Сначала применять ограничения источника, дат и области действия. Решение
   выбирает среди рассмотренных свидетельств, но не продлевает TTL, не повышает
   confidence и не делает симулированный источник реальным.
7. При трёх и более наблюдениях проверять все относящиеся к текущему состоянию
   конфликты: одного решения недостаточно для обхода остальных. Несогласованные
   решения и новое активное противоречие снова блокируют значение. Не вводить
   правило «последний ответ всегда прав».

Готово, когда конфликт блокирует факт, явное решение возвращает пригодное
значение в поиск, история доступна, а новое противоречие снова требует проверки.
Миграция работает на чистой и заполненной базе; повторный запуск безопасен.

## Порядок небольших изменений

1. Исходный прогон и контракты.
2. Схемы/миграции + решения конфликтов + единый resolver + тесты.
3. Повторное открытие вопросов + тесты.
4. Заменяемый reply parser + валидация + интеграционные тесты.
5. Типизированные API/ошибки + действие в демо-интерфейсе.
6. Новая характеристика + полный сценарий расширения.
7. Реальная проверка свободного текста + общий прогон + документация.

Главный критерий приёмки: новый запрос → геоданные → неизвестное свойство →
вопрос → свободный ответ → подтверждение → изменившийся подбор → противоречие →
явное решение → повторный подбор. В демо влияние симулированных ответов проверять
с `include_simulated=true`; обычный поиск по-прежнему их исключает.
