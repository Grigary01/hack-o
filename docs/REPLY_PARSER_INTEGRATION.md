## Контракт с ML

Интерфейс находится в `app/hotelier/reply_parser.py`:

```python
class ReplyParser(Protocol):
    mode: str

    def parse(self, *, feature_key: str, text: str) -> ReplyExtraction: ...
```

Пример подключения готового обработчика ML-команды:

```python
from app.main import create_app
from app.schemas.hotelier import ReplyExtraction

class TeamReplyParser:
    mode = 'team_ml'

    def __init__(self, extractor):
        self.extractor = extractor

    def parse(self, *, feature_key, text):
        return ReplyExtraction.model_validate(
            self.extractor(feature_key=feature_key, text=text)
        )

# extractor — реализация ML-команды, не функция, придумывающая свойства.
app = create_app(reply_parser=TeamReplyParser(extractor))
```

Backend передаёт только `feature_key` и исходный текст. `hotel_id`, `question_id`,
источник, даты и confidence модель не задаёт. Отель и вопрос определяются по БД.
`ParsedHotelQuery` и форма `ReplyExtraction` (`claims`, `unparsed`, `parser_mode`)
сохранены. Импорт `dialogue.parse_hotelier_reply` по-прежнему доступен для старого
offline-разбора. Прямые вызовы `submit_answer()` могут передавать
`reply_parser=...`; без него остаётся прежний bounded parser.

## Режимы и настройка

Гостевой запрос и ответ отельера выбираются независимо:

```dotenv
PARSER_MODE=fixture
REPLY_PARSER_MODE=rules
```

| `REPLY_PARSER_MODE` | Поведение |
|---|---|
| `rules` | По умолчанию, сохранённый offline regex; `parser_mode=bounded_rules` |
| `fixture` | Явная заглушка ML из JSON; неизвестный текст требует уточнения |
| `ollama` | Готовый HTTP-адаптер `/api/chat` со схемой |
| `groq` | Готовый HTTP-адаптер structured outputs с серверным ключом |

Ollama использует существующие `OLLAMA_URL`, `MODEL_NAME`, `OLLAMA_NUM_CTX`;
Groq — `GROQ_API_KEY`, `GROQ_MODEL`. Timeout берётся из
`PARSER_TIMEOUT_SECONDS`. Ключ остаётся на backend. При выборе Groq текст ответа
отельера передаётся этому провайдеру; локальные rules/fixture не используют сеть.
Модель/хост можно также задать отдельной конфигурацией внедряемого адаптера.

Каждый вызов HTTP-адаптера ограничен timeout и одной попыткой. Нет скрытого
переключения на fixture или rules при ошибке. Клиент, переданный извне для теста,
адаптер не закрывает; собственный HTTP-клиент закрывается после запроса.

Схема и промпт формируются по текущей характеристике реестра, без каталога
отелей и ID из БД. Provider schema ограничивает `feature_key` значением вопроса;
backend проверяет это независимо. HTTP-запросы основаны на первичной документации
[Ollama chat](https://docs.ollama.com/api/chat) и
[Groq Structured Outputs](https://console.groq.com/docs/structured-outputs).
Groq используется в best-effort режиме с локальной обязательной валидацией.

## Что проверяет backend

- Структуру, неизвестные поля, конкретный цифровой номер, boolean `value`,
  целочисленный этаж либо `null`.
- Допустимость характеристики, её room/boolean scope и совпадение с вопросом.
- Непустую дословную цитату из исходного ответа; номер должен быть указан
  в цитате либо входить в её числовой диапазон.
- Мутацию Pydantic-объекта после создания: результат повторно валидируется,
  даже если обработчик уже вернул `ReplyExtraction`.
- Дубли утверждений: одинаковые объединяются, противоречия остаются
  неразобранными и требуют уточнения.
- Известные условные/сезонные/неуверенные формулировки: консервативный барьер
  добавляет `unparsed`, даже если модель попыталась вернуть безусловное значение.

Это структурная и ограниченная проверка привязки к тексту, не доказательство
истинности или полного понимания языка. Барьер условий может потребовать
переформулировки допустимого текста. Полярность, полноту и смысл разбора должен
проверить человек. Неполный разбор нельзя подтвердить; все факты демо-кабинета
остаются симулированными с прежней низкой уверенностью.

Поток: текст → обработчик → проверка → pending → просмотр человеком →
подтверждение → наблюдения. До подтверждения комнаты и наблюдения не создаются.
Перед подтверждением сохранённый разбор проверяется заново; ошибка не оставляет
частичных записей. Источник, цитаты, даты, TTL и история сохраняются.

## Подключение frontend и заглушки

URL и тело отправки ответа прежние:

```text
POST /api/hotelier/questions/{qid}/answer  {"text": "..."}
POST /api/hotelier/answers/{aid}/confirm   {"accept": true}
```

`QuestionClient` и существующий Streamlit не требуют нового формата запроса.
В `health` добавлено поле `reply_parser_mode`; оно сообщает выбранный режим,
а не готовность внешнего сервиса. `external_services_checked=false` сохранён.

| Результат | Что показать |
|---|---|
| 200 + pending | Предварительный разбор для проверки |
| 200 + `unparsed` | Требуется уточнить текст; подтверждение недоступно |
| 422 при confirm | Разбор неполный или больше не соответствует вопросу/тексту |
| 502 при answer | Обработчик вернул неподходящий JSON, цитату, номер или свойство |
| 503 при answer | Нет ключа/модели, timeout, исчерпана квота или сервис недоступен |

В последних двух случаях новый ответ и факты не записываются. Backend не
возвращает сырой текст ошибки провайдера или секреты. Существующий APIClient
передаёт эти ошибки в UI через RuntimeError.
Предыдущий предпросмотр сбрасывается при новом разборе, изменении текста или
выборе другого вопроса: старый черновик нельзя подтвердить под видом нового.

Для автономной разработки запустите backend с `REPLY_PARSER_MODE=fixture`.
Заглушка использует [явные примеры](../data/demo/hotelier_reply_fixtures.json),
включая `301: море видно. 302: окна во двор.`. Она не подбирает похожий пример:
замена номера на неизвестный приведёт к уточнению. Это тестовый режим.

Полные снимки API и схема для ML:
[reply_integration_fixture.json](examples/reply_integration_fixture.json).
Они содержат pending, подтверждение, условный ответ и ошибки 502/503;
все помечены как fixture/stub, `real_model_used=false`.
Обновление: `python -m scripts.export_reply_contract`.
