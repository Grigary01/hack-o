# Дополнительная проверка парсера, 29 октября 2026

`parser_stress_2026-10-29.jsonl` — 24 синтетических запроса, составленных coding assistant
после анализа ошибок на старых 32 запросах. Это **не реальные отзывы пользователей,
не независимая человеческая gold-разметка и не доказательство общего качества 90%**.

Ответы зафиксированы до первого запуска модели на этом наборе. SHA-256 файла:
`8045df9ac5be30f9b6106b782889d49279cccae5c535b924cf559acef4659c55`.
Разметка не меняется после просмотра предсказаний. У каждой записи есть автор
`coding_assistant`, `human_reviewed: false`, идентификатор и ожидаемый контракт.

Проверяем комбинации обязательных/желательных условий, отрицания и безразличие,
строгие числовые границы, километры, диапазоны, явные и относительные веса,
нулевой вес, числовые компромиссы utility, неопределённые минуты, неподдержанные
услуги и запрос без фильтров. Есть числа и сочетания, отсутствующие в demo.

Поле `split: held_out` нужно существующему CLI. По методологии это **новый
синтетический stress-набор**, а старые 32 `held_out` теперь являются development:
их ошибки уже использовались при разработке промпта. Запросы этого файла не
подключены к `query_messages`, FixtureQueryParser или OfflineQueryParser.

Для неоднозначных запросов точная фраза уточнения не является единственно
правильной. Exact match на них нужно читать с этой оговоркой. F1 целых требований
сравнивает только hard/soft; он НЕ проверяет правильность текста уточнения.

Запуск из корня проекта с установленной Gemma и запущенной Ollama:

```bash
python -m scripts.compare_parser --mode ollama \
  --dataset data/evaluation/parser_stress_2026-10-29.jsonl \
  --output runtime/parser_stress.json
```

Следующая независимая оценка: собрать запросы других участников/людей,
разметить до просмотра ответов модели, согласовать спорные случаи, не настраивать
промпт по финальному тесту. Старые спорные метки исправлять отдельной версией
датасета; затем пересчитать на новой версии и baseline, и новый вариант.
