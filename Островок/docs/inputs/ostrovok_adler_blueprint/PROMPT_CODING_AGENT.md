КРИТИЧНО: в `engines/map_search_engine/engine.py` матрица `calculate_distance_matrix(..., profile="foot")` внутри использует `geopy.distance.geodesic`, то есть **кратчайшее расстояние по поверхности Земли, не маршрут по дорожкам**. Профиль `foot` там лишь задаёт скорость для оценки длительности (`distance/1.4`). `demo.py` ранжирует близость эвристикой `1/(1+d/1000)` для объектов в пределах 2 км. **Нельзя писать в UI «420 метров пешком», если расстояние было получено геодезически.** Исправь семантику и тесты.

Проверь также README: в нём могут встречаться команды для `demo_vacation_search.py`, хотя файл в корне называется `demo.py`. Устрани рассогласование.

### Решения команды, которые уже приняты

1. **География — Россия, прибрежная часть Адлера (Сочи).** Не расширяй MVP на всю РФ. Конкретную границу области хранить в конфиге (bbox/полигон), выбрать после фактической проверки OSM. Цель — порядка **15–30 реальных отелей** внутри области. Не изобретай названия, OSM IDs или координаты.
2. **Извлечение пользовательских предпочтений:** LLM + **Structured JSON Output** + Pydantic + небольшие few-shot примеры + тестовый набор русскоязычных запросов. **Не обучать BIO/NER с нуля в MVP**, если нет объективной проблемы качества. BIO — опциональная baseline/альтернатива, не требование.
3. **Cosine similarity / embeddings:** НЕ использовать как основной фильтр расстояний и булевых фактов. Допускается позже для семантических текстовых описаний / свободных ответов отельеров. Не добавляй FAISS/векторную БД без необходимости.
4. **Геоданные:** OpenStreetMap/Overpass + `osmnx` + `networkx`; минимум одна реально **вычисленная** геохарактеристика — например, **пешее расстояние от входа отеля до доступного входа на пляж**. При отсутствии точных входов честно помечай вычисление приблизительным.
5. **Оркестрация:** Python tool registry / function calling с явным перечнем разрешённых инструментов. MCP **не обязателен**. Агент должен уметь для выбранной характеристики выбрать источник/инструмент, получить свидетельство, зафиксировать качество, спросить отельера при нехватке данных. Действительные Python-инструменты выполняют расчёты, не LLM.
6. **Демо и архитектура:** Python backend FastAPI, лёгкий фронтенд Streamlit (самостоятельный клиент к REST API), SQLite + SQLAlchemy для локальной базы; Pydantic для контрактов. Не вводи тяжёлый стек без доказанной необходимости. Дизайн должен позволять позже заменить UI на React.
7. **Demo-first:** всё необходимое для офлайн-демо заранее сохранить в `data/demo/`; не заставляй судей ждать долгие запросы Overpass и не требуй запуска большой локальной модели для просмотра демо. Онлайн-сбор — отдельная команда/режим.

## 2. ПОЛНЫЙ текст задачи организатора (переписан по предоставленному ТЗ)

> **🪄Трек «О!дин шаг до идеального отеля»**
>
> **Найди отель, который подходит именно тебе, даже если в описании об этом ни слова.**
>
> Трек про данные: как агенты могут узнавать об отелях то, чего нет ни в одной карточке. Подойдёт командам, которые работали с геоданными или готовы быстро в них разобраться.
>
> ### Проблематика
>
> Кому-то нужен вид на закат, а кому-то на главную достопримечательность города. Одни ищут тишину, другие хотят жить в гуще событий. Для одних важна детская площадка поблизости, для других — возможность выспаться за плотными шторами после долгой дороги.
>
> Стандартные фильтры отвечают только на типовые вопросы: звёзды, завтрак, Wi-Fi, бассейн. Ответы на всё остальное пользователь ищет сам. Он листает отзывы и фото, смотрит панорамы улиц и пишет отельеру. На это уходят часы. Одни пользователи устают и уходят, так ничего и не выбрав. Другие бронируют наугад и только на месте понимают, что отель им не подходит.
>
> При этом многое можно узнать заранее. Вид из окна вычисляется по рельефу и высоте соседних зданий. Шум можно оценить по дорогам, барам и железнодорожным путям рядом. Остальное знает отельер, просто его никто не спрашивает. Эти данные никто не собирает системно.
>
> Наша цель — чтобы пользователь с минимальными усилиями и как можно быстрее находил отель, который подходит именно ему. Для этого система должна знать об отелях то, чего нет в карточках, и уметь искать по этим знаниям.
>
> ### Формулировка задания
>
> Разработайте прототип агентной системы для Островка. Система должна собирать уникальные характеристики отелей и номеров из открытых данных и у отельеров, систематизировать, хранить и показывать пользователю.
>
> Мы не даём участникам ни API, ни MCP-серверов, ни данных Островка. Всё собираете сами: список отелей, данные о них, инструменты агентов, логику, интерфейс. Источники — открытые данные: OpenStreetMap, карты высот, публичные датасеты и API.
>
> Основная сложность — не придумать характеристику, а достоверно её получить. Нужно понять, откуда агент её берёт, насколько он в ней уверен, как её проверить и когда она устареет. Агент, который просто просит LLM «угадать, есть ли в отеле вид на море», — это не решение.
>
> ### Примеры для вдохновения
>
> Это примеры, а не обязательный список. Чем больше своих идей и proof of concept вы придумаете, тем лучше.
>
> **Вычислить по геоданным**
> - **Вид на закат или на достопримечательность.** Построить карту высот: рельеф берём из открытых DEM, например SRTM или Copernicus, высоты зданий — из OpenStreetMap. Дальше проверить прямую видимость от окна до Эйфелевой башни или до горизонта на западе. Учесть этаж и сторону фасада и рассчитать положение солнца по датам. Итог может выглядеть так: «закат из окон западной стороны, с 5-го этажа, апрель — август».
> - **Вид на море или горы.** По той же карте высот посчитать, какую часть моря или горного хребта видно из окон и начиная с какого этажа.
> - **Тишина.** Оценить шум с каждой стороны здания: учесть дороги и их класс, железную дорогу, бары и ночные клубы, близость аэропорта. Для Европы есть открытые карты шума.
> - **Реальная доступность.** Считать путь до пляжа, метро или центра по реальному пешему маршруту с учётом перепада высот, а не по прямой. Отдельно отметить, нужно ли переходить оживлённую трассу.
> - **Что работает ночью.** Круглосуточные аптеки, магазины и кафе рядом — по `opening_hours` из OpenStreetMap.
> - **Для семей с детьми.** Детские площадки, пешеходные улицы, расстояние до ближайшей детской больницы.
> - **На машине.** Можно ли подъехать к входу или отель в пешеходной зоне, где парковаться, есть ли рядом зарядки для электромобилей.
> - **Дорога из аэропорта.** Время в пути на общественном транспорте по открытым расписаниям GTFS, нужны ли пересадки, ходит ли транспорт ночью.
>
> **Найти в других открытых источниках**
> - **Погода и климат по месяцам.** Температура воздуха и воды, число солнечных дней, сезон дождей — например, по историческим данным Open-Meteo. «В октябре здесь ещё купаются».
> - **Качество воздуха.** Например, по данным OpenAQ.
> - **Связь для удалённой работы.** Вышки сотовой связи рядом с отелем и их стандарты (4G, 5G), например по OpenCellID.
> - **Стройки и мероприятия рядом.** На городских порталах открытых данных есть разрешения на строительство, перекрытия улиц и фестивали. Строительство под окнами в даты поездки — тоже характеристика.
> - **История здания.** Отель в особняке модерна 1905 года или в бывшей фабрике — это можно узнать из Wikidata и Википедии.
> - **Фото с геометками.** По открытым снимкам, например из Wikimedia Commons или уличным панорамам Mapillary, можно определить, что видно с улицы: фасад, балконы, терраса на крыше.
>
> **Узнать у отельера**
> - **Вопрос отельеру.** Если данных нет или агент в них не уверен, он сам формулирует вопрос: «Какие номера выходят на запад?», «Есть ли в номерах шумоизоляция?». Отельер отвечает в свободной форме, а агент раскладывает ответ по нужным полям.
> - **С питомцем.** Каких животных и до какого веса пускают, сколько это стоит. Есть ли рядом площадка для выгула.
>
> ### User Story
>
> **Как путешественник**, я хочу быстро найти отель по своему запросу, чтобы на месте всё оказалось именно так, как я хотел.
>
> **Как компания Островок**, я хочу знать об отелях больше, чем написано в их карточках. Тогда мы будем точнее подбирать отели гостям, конверсия будет расти, а отмен станет меньше.
>
> **Как отельер**, я хочу, чтобы о сильных сторонах моего отеля узнали те гости, которым они важны. И чтобы на вопросы об отеле можно было ответить один раз, а не в каждой переписке.
>
> Мы в Островке ценим свежие идеи и нестандартные подходы и никак не ограничиваем вас в выборе технологий, моделей и архитектуры. Вы сами решаете, какие характеристики собирать, из каких источников, как агенты распределяют работу, когда считать по данным, а когда спрашивать отельера.
>
> ### Ожидаемый результат
>
> Работающий прототип для набора отелей выбранного региона, в котором пользователь может найти отель по собранным системой характеристикам.
>
> Мы рекомендуем сосредоточиться на одном регионе и не распыляться на несколько сразу: лучше глубоко проработать один, чем поверхностно охватить много.
>
> Проект должен запускаться по инструкции из README, без многочасовой загрузки данных: положите в репозиторий заранее собранные демо-данные. Если для работы нужен ключ LLM, опишите это в README и приложите `.env.example`.
>
> ### Основные задачи
>
> 1. **Сбор характеристик.** Агент сам решает, какие источники и инструменты нужны для конкретной характеристики, и получает её значение. Хотя бы одна характеристика должна вычисляться по геоданным, а не просто находиться в тексте.
> 2. **Диалог с отельером.** Если данных не хватает, агент задаёт вопрос отельеру, принимает ответ в свободной форме и раскладывает его по нужным полям. Отельера можно имитировать.
> 3. **Хранение и достоверность.** У каждого значения есть источник, уверенность и дата получения. Если источники противоречат друг другу, система это замечает и разбирается.
> 4. **Расширяемость.** Новую характеристику можно добавить без переписывания системы, например описав её текстом.
> 5. **Поиск по запросу.** Пользователь описывает своими словами, что ему важно, например «тихий номер с видом на закат недалеко от моря», и получает подходящие отели.
>
> ### Дополнительные задачи
>
> 1. **Объяснение выбора.** Система объясняет, почему отель подходит под запрос, а в чём не дотягивает: «вид на закат есть, но только с 5-го этажа».
> 2. **Сравнение отелей.** Пользователь сравнивает несколько отелей или номеров по собранным характеристикам.
> 3. **Кабинет отельера.** Отельер видит, что система узнала о его отеле, подтверждает или исправляет значения и отвечает на вопросы агента.
> 4. **Актуализация.** Система повторно проверяет устаревшие данные и реагирует на изменения, например рядом построили дом и закрыли вид.
> 5. **Метрики качества.** Собственная размеченная выборка и замеры: точность характеристик, покрытие, доля вопросов к отельеру.

## 4. Заданный pipeline: конкретные технические контракты

### A. Query understanding — задача ML-разработчика

Вход: русский текст пользователя. Выход: типизированный `ParsedHotelQuery` с:

- `region`: фиксированный `Adler` для демо либо явно указанное пользователем местоположение внутри поддерживаемой области;
- `hard_constraints`: строгие ограничения со свойствами `feature_key`, `operator`, `value`, `unit`, `scope`;
- `soft_preferences`: желательные значения + `importance` (явная пользовательская настройка, не выдуманная точность);
- `negations` / `desired=false`: корректная обработка «не хочу рядом с барами»;
- `unknown_or_ambiguous`: то, что нельзя уверенно определить из текста;
- `clarification_question` (опционально) при необходимости;
- `original_text` для аудита и trace.

Пример:

```json
{
  "region": "Adler",
  "hard_constraints": [
    {"feature_key":"walking_distance_to_beach_m","operator":"<=","value":500,"unit":"m","scope":"hotel"}
  ],
  "soft_preferences": [
    {"feature_key":"quietness_proxy","desired":"high","importance":0.9,"scope":"hotel"},
    {"feature_key":"sea_view","desired":true,"importance":0.6,"scope":"room"}
  ],
  "unknown_or_ambiguous": [],
  "clarification_question": null,
  "original_text": "Хочу тихий отель не дальше 500 метров пешком от пляжа, желательно номер с видом на море"
}
```

Требования к parser:

- Используй Ollama + **JSON schema structured output**, Pydantic `model_validate_json`; температура 0–0.2; 5–10 несколько-сценарных few-shot примеров; `feature_key` — только из реестра/алиасов, неизвестное → отдельная категория, а не выдуманный tool.
- Не делай из «недалеко» произвольное строгое ограничение в 500 м. Без числа — мягкое предпочтение или уточнение.
- Не считай слово «тишина» подтверждением того, что отель тихий: parser анализирует только намерение пользователя.
- Поддержи отрицания, относительные приоритеты («море важнее кафе»), метры/километры, «пешком», «не более», «минимум», двусмысленности и room-vs-hotel scope.
- Предпочтение `importance`: если пользователь не задаёт числа, применяй явно задокументированные default weights; сохраняй признак `weight_source=default|explicit|relative_inferred` и предоставь UI-ползунки для корректировки. Не притворяйся, что LLM научно измерила важность.
- Поддержи `PARSER_MODE=ollama|fixture`; fallback/fixture-режим должен работать без GPU и API. Вместо бессодержательного regex-all добавь фиксированный набор проверенных тестовых запросов с корректными JSON-ответами.
- Сделай `data/evaluation/queries_gold.jsonl` на 40–60 **своих** разных русских запросов, где вручную прописано ожидаемое извлечение, и `scripts/evaluate_parser.py`: JSON exact-match плюс precision/recall/F1 по constraint/preference полям, отдельная проверка операторов, чисел и отрицаний. Эти метрики нельзя выдавать без фактического запуска.

### B. Feature agent / Tools — задача Agent + Backend

Инструменты с типизированными входами/выходами, явной регистрацией и безопасным диспетчером:

- `fetch_osm_hotels(region)`
- `fetch_osm_pois(region, category)`
- `get_pedestrian_distance(hotel_id, beach_access_id)`
- `calculate_quietness_proxy(hotel_id)` — **proxy потенциального внешнего шума**, не децибелы и не доказанная тишина в номере;
- `get_hotel_feature(hotel_id, feature_key)`
- `ask_hotelier(hotel_id, feature_key, question)`
- `parse_hotelier_reply(question_id, free_text)`
- `save_feature_evidence(...)`

Действия: когда значение отсутствует или устарело, agent/planner выбирает допустимый tool по feature schema, выполняет его, записывает evidence и решает: подтверждать факт, помечать неизвестным или спросить отельера. Реализуй **явный выбор инструмента** (LLM tool calling или constrained tool planner + реестр с видимым в logs решением; не называй жестко зашитую последовательность «автономным агентом» без объяснения). Никаких произвольных имён методов из ответа LLM, запросов SQL от LLM и бесконтрольных циклов. Лимит вызовов, таймауты, ретраи и ошибки.

### C. Геоданные — задача Geo/Data

- OSM/Overpass — реальные отели, пляжи и доступные проходы/входы, дороги, железная дорога, ночные заведения. Зафиксируй OSM IDs и дату выгрузки.
- OSMnx `network_type='walk'` → граф доступной пешей сети; NetworkX/Dijkstra (через API OSMnx) → сумма длин рёбер. Не подменяй маршрутизацию `geodesic`/Haversine. В результатах держать `distance_method='pedestrian_graph'`, `graph_snapshot_date`, `coverage_quality`.
- Лучший целевой объект — доступный вход/проход к пляжу, **а не ближайшая точка воды за забором**. Если точные входы не размечены, используй приблизительную метку, явно понизь достоверность/попроси проверить; не заявляй точность до метра. Проходы, тупики, отсутствующие элементы графа и маршруты, не найденные алгоритмом, должны обрабатываться.
- Выдели отдельный `geodesic_distance_m` для quick prefilter/диагностики с честным названием, а не «пешком».
- Для `quietness_proxy`: задокументированная эвристика по расстояниям/классам дорог, железной дороге, барам/клубам — **без утверждений о реальных дБ**. Не смешивай тишину района и шумоизоляцию номера.
- На MVP не вычисляй правдоподобный «вид на море/закат» без этажей/окон/высот; используй `unknown` и запрос отельеру. Модуль продвинутой прямой видимости (DEM/buildings) — P2.
- `scripts/collect_adler_osm.py`, `scripts/compute_geo_features.py`, `scripts/seed_demo.py` должны выполняться отдельно от старта сервера. Сохрани исходный геодамп/обработанные реальные данные в `data/demo/` в разумном объёме. Ограничения публичных API, атрибуцию и кеширование соблюдай. Не используй закрытые/нелегальные данные Островка.

### D. Схема фактов, достоверность и конфликты — Backend

Создай отдельные сущности `Hotel`, `Room` (опционально с поддержкой будущих room facts), `FeatureDefinition`, `FeatureObservation`, `Evidence`, `Source`, `Conflict`, `HotelierQuestion`, `HotelierAnswer`.

Каждое наблюдение хранит:

- `subject_type`, `subject_id`, `feature_key`, `value`, `unit`, `observed_at`, `collected_at`, `expires_at`;
- `source_type`, `source_name`, `source_ref/url/osm_id`, `method` (`osm_tag`, `routing`, `heuristic`, `hotelier_confirmed`, ...);
- `confidence_level` (`high|medium|low|unknown`) для КАЖДОГО наблюдения, опциональный `confidence` в `[0,1]` **только при осмысленной оценке**, и **расшифровку, как получено**, например heuristic rules; `quality_flags`; `raw_evidence_excerpt` / путь к snapshot;
- `status`: `verified`, `estimated`, `unknown`, `conflicted`, `stale`.

Не записывай придуманную вероятность `0.95` только потому, что LLM так сказала. Разделяй «доверие к источнику», «полнота OSM» и «валидность алгоритма». Если независимых калибровочных данных нет — confidence прямо обозначить как **эвристический**, не статистически откалиброванный.

Конфликты: два разных значения одного свойства для **того же отеля/номера и актуального периода** → сохранить обе версии, создать `Conflict`, пометить неопределённость и применить явное правило приоритета источников/свежести или спросить отельера. Не считать противоречием «рядом шумная трасса» и «номер с шумоизоляцией»: это разные характеристики.

### E. Search + Ranking — задача ML/Backend

- `hard_constraints` проверяй **детерминированно**, с правильными единицами и операторами. Объект с подтверждённым нарушением исключается. Неизвестное значение — отдельный `needs_verification`, а не автоматически «подходит» или «не подходит».
- Для мягких требований: простая прозрачная взвешенная оценка `sum(w_i * match_i) / sum(w_i)` по известным свойствам; отдельно `coverage` и penalties/неуверенность. Недостаток данных нельзя превращать в хороший score.
- Объяснение: какие требования соблюдены, какие нарушены, какие неизвестны, как считались расстояния и откуда сведения. Источники/даты должны быть доступны пользователю.
- UI может менять веса через ползунки и мгновенно пересчитывать ranking. Уместен `GET /api/hotels/{id}/evidence`.
- Embeddings/cosine-similarity — только отдельный P2 semantic-retrieval provider для описаний, не для числовых условий и не для «доказательства» геофактов.

### F. Диалог отельера — обязателен

При отсутствующей `room.sea_view` или неизвестной шумоизоляции агент формирует конкретный вопрос. В UI «Кабинет отельера (демо)» тестовый отельер отвечает свободным текстом, например «В номерах 301–305 вид на море, все на 3-м этаже». LLM/parser извлекает **room-specific** записи и исходную цитату, Pydantic проверяет, оператор/отельер может подтвердить или отклонить. После подтверждения значение записывается со `source_type='hotelier'`, датой, статусом, evidence. Важно: различать «утверждение отельера» и независимо проверенный факт.

## 6. REST API для интеграции команды

Минимально предложи и реализуй:

- `GET /api/health` — доступность backend и demo/db состояния;
- `POST /api/parse-query` — исходный текст → `ParsedHotelQuery` (для тестирования ML отдельно);
- `POST /api/search` — текст и/или готовый parsed JSON + optional slider weights → список кандидатов с `match`, `violated`, `unknown`, оценкой, объяснением и evidence;
- `GET /api/hotels` — список отелей;
- `GET /api/hotels/{id}` — карточка с доступными характеристиками;
- `GET /api/hotels/{id}/evidence` — доказательства и даты;
- `POST /api/hotelier/questions` — сформировать вопрос;
- `POST /api/hotelier/questions/{id}/answer` — свободный ответ;
- `POST /api/hotelier/answers/{id}/confirm` — сохранить или отклонить структурированные извлечения.

Схемы API, успешный ответ и ошибки положи в `docs/API.md`; обеспечь OpenAPI `/docs` через FastAPI. Код backend не должен зависеть от Streamlit. Не возвращай фиктивное «успешно», если данных или маршрута нет.

## 7. Визуальный демонстрационный сценарий

Пользователь вводит: **«Ищу тихий отель в Адлере, не дальше 500 метров пешком от пляжа, хотелось бы вид на море»**.

Ожидаемая демонстрация:

1. Выделились `walking_distance_to_beach_m <= 500`, `quietness_proxy=high`, `room.sea_view=true` (soft).
2. Система читает предвычисленные данные Adler/OSM (или считает, только если выбран online mode), отдаёт варианты с доказательствами расстояний и методами вычисления.
3. Неизвестный вид из номера НЕ превращается в «вид есть»; система предлагает спросить отельера.
4. В симуляторе отельер отвечает; parser извлекает structured room fact и сохраняет его с цитатой, временем и статусом.
5. Пользователь меняет вес тишины / вида — порядок результатов объяснимо меняется.
6. UI показывает сравнение 2–3 гостиниц, область неизвестного, источник данных и карту.

В демо должны быть **реальные отели** с проверенными OSM-идентификаторами; демонстрационные ответы отельера должны быть явно обозначены как **симулированные**, а не реальные свойства этих отелей. Не надо обещать, что все желаемые характеристики обнаружены.

## 8. Обязательные тесты и критерии приёмки

- Тест LLM-парсера/фикстур: единицы 0.5 км → 500 м, отрицания, «не больше», «желательно», city fallback Adler, отель vs номер, разные формулировки; некорректный JSON отклоняется.
- Тест геомаршрута на искусственном графе с препятствием: **длина маршрута больше геодезического расстояния**; случаи `no path`, ошибки OSM и качество `unknown`.
- Тест источника и конфликта: два взаимоисключающих сообщения о том же room feature; сохранить обе версии, показать conflict, не подменять факты.
- Тест отельера: вопрос → свободный ответ → извлечённые room facts → подтверждение → сохранение с source/date/evidence.
- Тест ранжирования: hard violated исключается, unknown требует подтверждения, изменение weights меняет ranking (когда данные различаются), обоснование связано с реальными характеристиками.
- API smoke: `GET /api/health`, `POST /api/search` в demo mode должны работать без живого Overpass и без Ollama на заранее согласованных fixtures.
- Факт скачивания/подготовки 15–30 отелей и использованных геоданных проверять отдельно. Не заполнять недостающие отели случайными вымышленными адресами.

### Definition of Done текущего этапа

Считаем этап выполненным, когда: структура репозитория ясна всем четырём ролям; `README` содержит точные команды; API и Streamlit запускаются с сохранёнными демо-данными; хотя бы один запрос проходит parser → подбор → объяснение; маршрут уже вычислен по пешеходному графу и имеет evidence; симулированный отельер может дать новое свойство; тесты выполнены либо честно отмечены как недоступные.
