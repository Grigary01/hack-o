# Архитектура прототипа — Островок / прибрежный Адлер

> **Статус:** целевая архитектура и проектный план, а **не описание уже написанного приложения**. Исходный проект: <https://github.com/MaximShalankin/agent_tool_map>. Для coding-агента — `PROMPT_CODING_AGENT.md`. Ответственным по задачам — `TEAM_TASKS.md`.

## 1. Задача для команды — за минуту

Пользователь: «Хочу тихий отель в Адлере, не дальше 500 метров **пешком** от пляжа. Желательно с видом на море».

Наш прототип должен:

1. Правильно извлечь из русского запроса ограничения и пожелания.
2. Найти отели на небольшом выбранном участке **Адлера (Россия)** в заранее собранных открытых данных.
3. **Рассчитать** минимум одну характеристику геоалгоритмом: пешеходное расстояние до доступного пляжа по OSM-графу.
4. Узнать/оценить другие характеристики: приблизительную интенсивность потенциального внешнего шума, наличие POI, сведения о номере из диалога с отельером.
5. Для **каждого значения** показать источник, метод, дату и уровень неопределённости; обнаруживать конфликты и устаревание.
6. Отфильтровать по строгим условиям, ранжировать оставшиеся варианты по желаниям и объяснить решения пользователю.
7. Позволить отельеру подтвердить или исправить неизвестное свойство в свободном тексте.

**Ограничение:** реальные данные Островка нам не предоставлены. Мы **не** утверждаем, что конкретный номер имеет определённый вид/шумоизоляцию, если это не подтверждено. Симулированные ответы отельера демонстрируют механику, а не реальное свойство гостиницы.

## 3. Два независимых pipeline

### A. Offline ingestion: получение достоверных фактов

```text
OpenStreetMap / Overpass  ─┐
                           ├→ реальные POI + OSM ID + координаты + collected_at
Карта пешеходных путей OSM ─┘                    │
                                                ▼
                                 OSMnx walking graph + маршруты
                                                │
              Обобщённые правила noise proxy ───┤
                                                ▼
                     Feature Observation + Evidence + provenance
                                                │
                                        SQLite + demo fixtures
```

- Сбор запускается **отдельным скриптом**, а не при каждом запросе пользователя.
- Источники: OSM для дорожек, пляжей, отелей, баров, железной дороги и POI; Open-Meteo позже для исторического климата; Wikidata позже для истории зданий.
- Честно различать `real_osm_data`, `derived_estimate`, `hotelier_simulated`, `not_available`.
- Из OSM нельзя автоматически получить реальные `price`, `occupancy`, `room_number`, `sea_view`, `soundproofing`: это `unknown`, если отельер не ответил.

### B. Online search: быстрый ответ пользователю

```text
текст пользователя
  → LLM structured extraction (или demo fixture)
  → Pydantic validation / normalization / feature aliases
  → ParsedHotelQuery {hard_constraints, soft_preferences}
  → загрузка предварительно вычисленных отелей и FeatureObservation
  → для отсутствующих/устаревших данных: Source Planner выбирает tool / вопрос отельеру
  → hard filter (true / false / unknown)
  → transparent weighted ranking + coverage + uncertainty
  → explanation с source/date/method
  → REST API → Streamlit UI
```

**Нельзя** заставлять LLM «самой узнать, виден ли пляж». LLM понимает текст или выбирает разрешённый инструмент. Геофункция считает путь. Ответ отельера — отдельный исходный источник и подлежит подтверждению.

## 4. Контракт между ML, Backend и Geo

### 4.1. Что принимает ML

`POST /api/parse-query`:

```json
{"text":"Ищу тихий отель в Адлере, не дальше 500 метров пешком от пляжа, желательно вид на море"}
```

### 4.2. Что ML обязан вернуть

```json
{
  "region": "Adler",
  "hard_constraints": [
    {
      "feature_key": "walking_distance_to_beach_m",
      "operator": "<=",
      "value": 500,
      "unit": "m",
      "scope": "hotel"
    }
  ],
  "soft_preferences": [
    {"feature_key": "quietness_proxy", "desired": "high", "importance": 0.9, "weight_source": "default", "scope": "hotel"},
    {"feature_key": "sea_view", "desired": true, "importance": 0.6, "weight_source": "default", "scope": "room"}
  ],
  "unknown_or_ambiguous": [],
  "clarification_question": null,
  "original_text": "Ищу тихий отель в Адлере, не дальше 500 метров пешком от пляжа, желательно вид на море"
}
```

Этот JSON — **иллюстрация контракта**, а не результат прогонки Gemma. Числа `0.9` и `0.6` — пример **настраиваемых весов по умолчанию**, не вычисленная «психологическая важность». В настоящем проекте веса должны описываться в `registry.yaml` или UI и корректироваться пользователем.

ML не пишет SQL и не вызывает произвольные URL. Бэкенд решает, какие уже существующие факты читать, какие инструменты доступны, как отбирать и ранжировать результаты.

### 4.3. Что возвращает Geo-инструмент

```json
{
  "subject_type": "hotel",
  "subject_id": "osm:way:EXAMPLE_ID",
  "feature_key": "walking_distance_to_beach_m",
  "value": 420,
  "unit": "m",
  "method": "pedestrian_graph",
  "source_type": "openstreetmap",
  "source_ref": "osm-snapshot-id",
  "collected_at": "2026-10-23T12:00:00Z",
  "confidence_level": "low",
  "confidence": null,
  "confidence_method": "heuristic_uncertain_beach_entry",
  "quality_flags": ["entry_point_approximate"],
  "status": "estimated"
}
```

`EXAMPLE_ID`, 420 м и дата **условные** — только пример схемы! Их нельзя публиковать в результатах демо как достоверные значения. Если confidence является числом, он обязан иметь задокументированную эвристическую/эмпирическую методику; `null` допустим, если уверенность не оценена.

### 4.4. Что возвращает поиск

Для каждого кандидата:

- `hotel_id`, `hotel_name`, при наличии — координаты для карты;
- `eligible: true|false|unknown` для strict filters;
- `matched_constraints`, `violated_constraints`, `unknown_constraints`;
- `score` от 0 до 1 для известных мягких предпочтений;
- `evidence_coverage`, `uncertainty`, `feature_explanations`;
- `evidence[]` с датой, источником, методом и ограничениями точности;
- `pending_hotelier_question_ids` для неизвестных room-фактов.

Если жёсткое ограничение подтверждённо нарушено — отель исключается из подходящих. Если не хватает данных — отель показывается отдельно как кандидат **«нужно уточнить»**. Никаких фальшивых «100% match».

## 5. ML — что делаем и что НЕ делаем

| Решение | Почему |
|---|---|
| **LLM + schema constrained JSON + Pydantic** | Работает с сочетаниями чисел, отрицаний, приоритетов, разными формулировками без дорогого обучения |
| Few-shot с русскими примерами | Можно быстро улучшить качество извлечения именно на задачах отелей |
| 40–60 вручную размеченных «текст → gold JSON» | Получаем честные метрики и примеры крайних случаев |
| Без обучения BIO/CRF как P0 | Сначала нужна работающая система, а не ещё одна разметка токенов |
| Без cosine similarity как P0 | Семантическое сходство не проверяет `<= 500 метров` и не подтверждает вид из окна |
| Эмбеддинги для свободных описаний как P2 | Возможны при накоплении текстовых наблюдений, после детерминированных фильтров |

**Улучшение исходного GitHub:** заменить `SearchParams` на корректные typed constraints/preferences, убрать извлечение случайного `{...}` из LLM-ответа, использовать JSON schema + Pydantic, добавить проверку алиасов `море` / `пляж` / `вид на море` (это **разные** фичи), числа и отрицания. Логировать parser mode и ошибки.

## 6. Геоданные с нуля

**OSM** — открытая карта с отелями, дорогами, пешеходными дорожками, пляжами и тегами. **Overpass** — API получения выбранных объектов из OSM. **OSMnx** — скачивает/конструирует граф пешеходной сети. **NetworkX** — алгоритм кратчайшего пути (в OSMnx уже есть нужная интеграция). **Folium** — визуализирует точки и полученный маршрут.

Есть два разных расстояния:

- `geodesic`: кратчайший путь на модели земной поверхности. Полезен для грубого поиска поблизости, **не учитывает проходимость**.
- `pedestrian_graph`: сумма длин рёбер реальной пешеходной сети. Это правильная основа для требования пользователя «500 метров пешком», с оговорками о неполной разметке и входах/выходах.

Маршрут не всегда строится; тогда верни `unknown` и причину, **не fallback на geodesic с подписью «пешком»**.

Почему Адлер: туристические пожелания (море, пляжи, дороги, потенциальный шум) можно продемонстрировать на небольшом участке. Но достаточность конкретных OSM-тегов надо **проверить при сборе**, а не предполагать. Факт наличия карты не гарантирует, что пляжные входы или этажи отелей размечены.

## 7. Реестр MVP-характеристик

| `feature_key` | Scope | Тип | Источник | Вычисление / защита от неверных утверждений | P |
|---|---|---|---|---|---|
| `walking_distance_to_beach_m` | hotel | число, метры | OSM paths + beach access | реальный пеший маршрут; пометка неточных входов | P0 |
| `quietness_proxy` | hotel/exterior | категория / 0–1 | OSM roads/rail/bars | эвристика риска внешнего шума; **не** реальная тишина в номере | P0/P1 |
| `sea_view` | room | bool/unknown | отельер; позже DEM и sightline | без подтверждения статус `unknown` | P0 (через диалог) |
| `soundproofing` | room | bool/unknown | отельер | запрос и подтверждение; не выводится из OSM | P1 |
| `night_open_pharmacy_nearby` | hotel | bool/distance | OSM `opening_hours` | только если часы заполнены/интерпретированы | P1 |
| `walking_distance_to_cafe_m` | hotel | число, метры | OSM + pedestrian graph | считать до доступного кафе; неизвестное ≠ нет кафе | P1 |
| `monthly_climate` | region | статистика | Open-Meteo history | история не предсказывает конкретную погоду в поездку | P2 |
| `building_history` | hotel | текст | Wikidata | только подтверждённое совпадение ID здания | P2 |
| `sunset_view` | room | bool/unknown | отельер; позже DEM + height | не путать расположение отеля с видом из окна | P2 |

**Расширение:** YAML декларация + существующий tool/provider для поддержанных видов фактов. Если требуются новые геовычисления, **придётся написать соответствующий calculator**. «Добавить характеристику текстом» не означает, что LLM может без нового инструмента достоверно вычислить что угодно.

## 8. Данные, происхождение, уверенность

Для каждого значения хранить минимум:

```text
subject_type / subject_id (hotel | room)
feature_key / value / unit
source_type / source_ref / raw evidence or snapshot
method / collected_at / observed_at / expires_at
confidence (optional) / confidence_method / quality_flags
status (verified | estimated | unknown | conflicted | stale)
```

Противоречия обнаруживаются между **двумя наблюдениями одной характеристики одного subject за совместимый период**. Сохраняйте версии; эскалируйте, а не стирайте «неудобное» свидетельство. Пример: «номера 301–305 имеют вид на море» vs «номер 302 не имеет вида на море». Это конфликт. «Громкая улица» vs «хорошие стеклопакеты» — не конфликт.

Если отельер отвечает свободно, выделите структуру и **цитату/trace**, попросите подтверждение исправления и лишь затем используйте как `hotelier_claim`, а не независимую геопроверку.

## 9. Frontend и backend, без взаимного смешения

### Backend (`app/`, FastAPI)

- `/api/parse-query` — JSON из русского текста;
- `/api/search` — hard/soft ranking + explanation/evidence;
- `/api/hotels`, `/{id}`, `/{id}/evidence`;
- `/api/hotelier/questions`, `/answer`, `/confirm`;
- `/api/health` — демонстрационный статус и работоспособность.

Контракты через Pydantic; SQLite через SQLAlchemy. Никакого прямого SQL из Streamlit. Сервис независимо тестируется через HTTP и Swagger `/docs`.

### Frontend (`frontend/`, Streamlit)

- Строка запроса на русском, кнопка «Найти»;
- распознанные предпочтения + ползунки веса (открыто и изменяемо);
- результаты с оценкой, строгими/мягкими условиями, неизвестными данными, доказательствами;
- карта отелей/маршрутов, без ложных точных значений;
- карточка сравнений 2–3 отелей;
- «Отельер (демо)»: очередь вопросов, свободный ответ, предварительная структура и подтверждение.

Фронтенд работает только с API. Если HTTP API недоступно, UI показывает явную ошибку, а не подделывает удачный поиск.

## 10. Demo, тесты и воспроизводимость

**Важно для судей:** `data/demo/` содержит уже собранный небольшой срез проверенных реальных OSM-отелей и маршрутов. Сбор вживую не делается при `uvicorn`/`streamlit run`.

- `DEMO_MODE=true` работает без внешних API, местного Ollama и длительной загрузки (через зафиксированные test queries/fixtures). Если запрос не входит в набор, UI честно сообщает об ограничении demo parser.
- `DEMO_MODE=false` / `PARSER_MODE=ollama` использует настроенную Ollama с выбранной моделью; модель и GPU требования документированы.
- В `.env.example` нет реальных API ключей; API/тайлы соблюдают лицензии и rate limits.
- Метрики: extraction field-F1/exact JSON match на gold queries; geodata coverage (% отелей с успешным маршрутом), observation coverage, конфликтная доля, доля вопрос-эскалаций. **Не выдавайте числа без измерений.**
- Тесты: invalid JSON, отрицания, metres/km, 2 разных веса, mock OSM, искусственный граф с преградой, no path, conflict, hotelier extraction, API smoke.

## 11. Definition of Done / следующий шаг

**P0 (обязательный вертикальный срез)**: 1 запрос → корректный JSON → сохранённый реальный отель → предвычисленный пеший маршрут → hard filter/ranking → объяснение с источником → карточка UI; симуляция вопроса отельеру → подтверждение ответа → сохранённый room fact.

**P1**: добавление шума-proxy, корректная обработка конфликтов и ползунки, сравнение, 40–60 gold queries, метрики, второй источник/feature.

**P2**: полноценная проверка линии видимости, климат/история зданий, embeddings для описаний, плановая актуализация, замена frontend на React при необходимости.

До создания PR каждому участнику надо увидеть `docs/PROJECT_STRUCTURE.md`, `docs/API.md` и понимать точку интеграции своей части.
